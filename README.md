# MNP Internal System — Phase 1

ระบบคำร้องและอนุมัติภายในแบบ paperless สำหรับพนักงาน MNP สร้างด้วย Next.js, TypeScript, Supabase Auth/Postgres/Storage และ LINE OA integration

## Pilot Web บน GitHub Pages

### NCR: ต้นทุนความสูญเสีย ผลดำเนินการ และแดชบอร์ด

ใช้กับ NCR จริงโดยแผนก QA, ผจก.โรงงาน และผจก.แผนกที่รับผิดชอบ (ผู้มีสิทธิ์แก้ไขความสูญเสียตาม `private.can_edit_ncr_losses`) และ Admin ลองซ้ำได้ในโหมดทดสอบระบบ (เลือก persona QA หรือผู้จัดการที่รับผิดชอบ) ด้วยข้อมูลที่แยกจากของจริง ส่วนต่อไปนี้ใช้ชุดเดียวกันทั้งสองโหมด:

- ผลดำเนินการจริง: คัดแยก ซ่อมสำเร็จ ทิ้ง ส่งคืน ยอมรับใช้ได้ และชั่วโมงเครื่องหยุด กิจกรรมคัดแยกแยกจากผลสุดท้ายเพื่อไม่รวมชิ้นเดียวกันซ้ำ ผลที่ยืนยันแล้วต้องมีหลักฐานอ้างอิง
- รายการค่าเสียหาย: เลือกประมาณการหรือยืนยันแล้ว ค่าซ่อม (Repair) กับ Rework เป็นคนละประเภทและรายงานแยกกัน แต่ละประเภทแยกค่าแรง วัสดุ และค่าจ้างภายนอก; ผลิตทดแทนเก็บเฉพาะค่าใช้จ่ายส่วนเพิ่ม เงินชดเชย/เครดิต/ขายซากเป็นรายการรับคืนแยกต่างหาก
- ใช้ “แก้ไข/ยืนยันยอด” เพื่อปรับรายการเดิมจากประมาณการเป็นยอดจริง ไม่เพิ่มรายการซ้ำ มีประวัติและ audit เมื่อแก้ไข
- การประเมินครบ: ต้องไม่มีรายการประมาณการ/รายการเดิมค้าง และยืนยันผลดำเนินการแล้ว ถ้าไม่มีค่าเสียหายต้องระบุเหตุผล การเพิ่ม แก้ไข หรือยกเลิกต้นทุนจะยกเลิกเครื่องหมายประเมินครบเพื่อให้ตรวจอีกครั้ง
- Dashboard NCR (`#/ncr-dashboard` เปิดจากปุ่ม **แดชบอร์ด NCR** ข้างปุ่ม **ออก NCR** ในหน้า NCR ที่ คำร้อง → NCR/CAR): การ์ดสรุป 4 ใบ (จำนวน NCR และ % ปิด, ใบค้าง/เกินกำหนดตอบ, สูญเสียสุทธิยืนยัน พร้อมประมาณการและรายการเดิมแยก, ความครบของการประเมินต้นทุน) รายการ "ต้องลงมือตอนนี้" แนวโน้มรายเดือน Pareto ข้อบกพร่อง ความสูญเสียแยกประเภท (ยืนยัน + ประมาณการ ค่าซ่อมแยกจาก Rework แตะแท่งเพื่อกรองใบที่มีต้นทุนประเภทนั้น) ตารางแผนก แหล่งที่พบ สาเหตุ 4M+E และผลดำเนินการตามหน่วย ทุกตัวเลขคำนวณจากรายการ NCR ชุดเดียว (`modules/ncr-dashboard-model.js` พร้อมเทสต์) แตะรายการเพื่อดูตัวเลขในหน้าและกรองทั้งหน้า จำนวน NCR นับเต็มใบเสมอ ส่วนบาทแบ่งตามสัดส่วนแผนก ผลทิ้ง/ซ่อมใช้เฉพาะผลที่ยืนยัน แยกหน่วย และไม่คำนวณอัตราของเสียทั้งโรงงานจากข้อมูล NCR
- ฐานเวลาเดียว: ทุกตัวเลขนับจากใบที่ออกในช่วงที่เลือก มูลค่าคือยอดสะสมของใบนั้น (ค่าใช้จ่ายที่เกิดทีหลังยังนับเข้าใบเดิม) SLA ตอบ 5 วันเริ่มนับเมื่อใบเข้าขั้น "รอแผนกตอบ" จาก `ncr_status_history` (ส่งกลับมาตอบใหม่เริ่มนับใหม่) ขั้นรอ ผจก.โรงงานพิจารณายังไม่นับ จึงต่างจากป้าย "เกินกำหนดตอบ" ในทะเบียน NCR ที่นับจากวันออกใบ ความครบของการประเมินนับตั้งแต่ขั้นรอแผนกตอบเป็นต้นไป

ส่วนนี้ใช้กับข้อมูลจริงและโหมดทดสอบเหมือนกัน (เดิมทดลองเฉพาะ sandbox) ข้อมูลสองโหมดยังแยกกันที่ฐานข้อมูล (`ncr_reports.is_test`): `app_ncr_record_loss` / `app_ncr_save_outcome` ตรวจสิทธิ์แก้ไขความสูญเสียและตรวจว่าผู้ทำรายการกับใบอยู่โหมดเดียวกัน ข้ามโหมด = `SANDBOX_SCOPE_MISMATCH` การอ่านใช้ RLS ไม่ใช้ flag ฝั่ง browser เป็นการตรวจสิทธิ์ การแนบไฟล์ยังใช้ไม่ได้เฉพาะในโหมดทดสอบ

ต้องนำ migration `20261005090715_ncr_loss_outcomes_dashboard.sql` และ `20261006040000_ncr_costs_outcomes_live.sql` (เปิด RPC ทั้งสองให้ใช้กับใบจริง) ขึ้นผ่านกระบวนการ deployment ที่อนุมัติก่อนเผยแพร่ assets รุ่น `20261006f` Migration เพิ่มข้อมูลโดยไม่ลบยอดเดิม ยอดเก่าของใบจริงเป็น `legacy` และไม่ถูกนับเป็นยอดยืนยัน (การ์ดใบในทะเบียนแสดง "สุทธิยืนยัน · รอยืนยัน n รายการ" และ Dashboard แยกยอดรายการเดิม) จนกว่าผู้มีสิทธิ์จะกด "แก้ไข/ยืนยันยอด" ต้นทุนต่อหน่วยเก็บเป็นอัตราของรายการในวันที่บันทึก

ข้อมูลประกอบเก็บใน `ncr_outcomes` (หนึ่งผลปัจจุบันต่อ NCR สินค้า/ล็อตเดียว) และ `ncr_losses` (หนึ่งค่าใช้จ่าย/ชดเชยต่อรายการ) ถ้าอนาคต NCR รองรับหลายสินค้า ต้องขยาย key ของผลดำเนินการเป็นรายการสินค้า/ล็อตด้วย

การตรวจ: `npm run test:unit` รวมการทดสอบสูตร/งวด/การนับใบ/ข้อมูลขาด และ `npm run db:test` รวม `ncr_loss_outcomes.test.sql` ตรวจ RLS, sandbox isolation, สิทธิ์ API ทั้งข้อมูลจริงและโหมดทดสอบ, validation, การยืนยันยอดในรายการเดิม และการยกเลิกผลประเมินครบ โดย CI รันกับ Supabase local เท่านั้น

หน้าเว็บทดลองใช้งานจริงอยู่ที่ [https://mnpchatai.github.io/MNP_SYSTEM/](https://mnpchatai.github.io/MNP_SYSTEM/) โดยไฟล์ `index.html`, `styles.css` และ `app.js` เป็น static client สำหรับ GitHub Pages และเชื่อมต่อ Supabase Cloud ผ่าน publishable key

- รองรับการเข้าสู่ระบบด้วยรหัสพนักงาน
- มีบัญชีทดสอบแยกบทบาทผู้ขอ ผู้อนุมัติ และผู้ปฏิบัติงาน
- การสร้างคำร้อง การอนุมัติ และการเปลี่ยนสถานะเรียก Postgres RPC ที่ตรวจ session/สิทธิ์ฝั่งฐานข้อมูล
- การลงทะเบียนบัญชีทดสอบเรียก `pilot-auth` Edge Function และต้องใช้ invite code ที่ไม่อยู่ใน repository
- GitHub Pages ไม่มี server runtime ดังนั้น LINE webhook/OAuth และฟังก์ชันที่ใช้ server secret ยังคงต้องรันบน Supabase Edge Functions หรือ deployment แบบมี server
- **ทุกครั้งที่แก้ `app.js`, `styles.css` หรือไฟล์ใน `modules/` ต้องเลื่อนเลข `?v=` ใน `index.html` ด้วย** ทั้งสองไฟล์ใช้ป้ายรุ่นชุดเดียวกัน (`?v=20260921e`) เพราะเปลี่ยนคู่กันเสมอ ถ้าไม่เลื่อน เบราว์เซอร์ที่เคยเปิดเว็บแล้วจะยังใช้ไฟล์เก่าจาก cache ต่อไป แล้วดูเหมือน deploy ไม่ติด — GitHub Pages ไม่มี build step จึงไม่มี content hash ให้อัตโนมัติ ต้องเลื่อนเอง (ใช้วันที่ deploy เป็นเลขรุ่นได้เลย) ส่วนแท็บที่เปิดค้างไว้ก่อน deploy ระบบจะเทียบเลข `?v=` ของ `app.js` กับ `index.html` ล่าสุดทุกครั้งที่ผู้ใช้กลับมาที่แท็บหรือเปลี่ยนหน้า (เว้นช่วงอย่างน้อย 1 นาที) ถ้าไม่ตรงจะขึ้นปุ่ม "มีระบบเวอร์ชันใหม่ · แตะเพื่อโหลด" ให้ผู้ใช้กดรีโหลดเอง
- **โมดูลคำร้องที่ flow ต่างจากโมดูลอื่น** แยกไฟล์ไว้ที่ `modules/<module>.js` (Pilot Web) และ `src/lib/request-modules/<module>.ts` (Next.js) โมดูลลงทะเบียนตัวเอง (`window.MNP_REQUEST_MODULES` / `separateRequestModules`) แล้วใช้หน้า "สร้างคำร้องใหม่" และฟังก์ชันส่งคำร้องกลางร่วมกับโมดูลอื่น ตั้งชื่อไฟล์เป็นตัวพิมพ์เล็กคั่นด้วย `-` (เช่น `module-it`) ไม่มีช่องว่าง ไฟล์ใน `modules/` ต้องโหลดใน `index.html` ก่อน `app.js` การ์ดจะแสดงเมื่อโมดูล `enabled` และ `request_types.is_active` ในฐานข้อมูลเปิดทั้งคู่ ตอนนี้มี `MT_REPAIR` (ใบคำร้อง/แจ้งซ่อม MT) ที่ `modules/module-mt.js`, `NCR_CAR` (NCR/CAR) ที่ `modules/module-ncr.js` และ `src/lib/request-modules/module-ncr.ts` ซึ่งยังใช้ฟอร์ม/flow คำร้องทั่วไป, `MANAGEMENT` (ใบคำร้องถึงฝ่ายบริหาร) ที่ `modules/module-mg.js` และ `src/lib/request-modules/module-mg.ts` ซึ่งใช้งานอยู่ และ `IT_REPAIR` (ใบแจ้งซ่อม IT) ที่ `modules/module-it.js` และ `src/lib/request-modules/module-it.ts` ซึ่งเปิดใช้แล้วด้วย flow คำร้องทั่วไป (หัวหน้าแผนกผู้แจ้ง → ผู้จัดการแผนก IT → ผู้ปฏิบัติงาน, ดู `20261001050000_enable_it_repair_module.sql`) ผู้มีสิทธิ์อนุมัติโมดูล IT กำหนดรายคนโดย Admin เท่านั้น (`20261001060000_it_repair_explicit_module_grants.sql`)

ไฟล์ Next.js เดิมยังคงเป็นสถาปัตยกรรมเป้าหมายสำหรับ production ที่รองรับ Server Actions และ Route Handlers ครบถ้วน ส่วน Pilot Web ใช้สำหรับทดสอบกระบวนการหลายผู้ใช้ในระยะนี้

### แดชบอร์ด MT (เวอร์ชันทดสอบ)

หน้า `#/mt-dashboard` เปิดจากปุ่ม **แดชบอร์ด MT** ข้างปุ่ม **สร้างคำร้อง / แจ้งซ่อม MT** ในหน้า คำร้อง → ใบคำร้อง/แจ้งซ่อม MT (โมดูลประกาศ `headerLinks` เหมือน NCR) ไม่มีเมนูข้างแยก ปุ่มย้อนกลับพาไปหน้า MT เดิม
อ่านข้อมูลผ่าน RLS ชุดเดียวกับหน้าคำร้อง (`requests`, `request_status_history`, `request_verifications`, `request_technicians`, `machines`, `employees`) ไม่มี migration/RPC ใหม่ จึงเห็นเฉพาะใบที่บัญชีนั้นมีสิทธิ์เห็น และไม่รองรับโหมดทดสอบ (Admin Sandbox) เหมือนโมดูล MT ส่วนอื่น

ส่วนที่ตอบ "งานค้างอยู่ที่ไหน ใช้เวลาเท่าไร" และ "อะไรเสียบ่อย ใครรับภาระ" ในหน้าเดียว ยังไม่มีสถิติรายเดือนแบบกราฟแนวโน้ม

- **งานค้างอยู่ที่ใคร**: จำนวนใบที่ยังไม่จบแยกตามขั้น (รอ ผจก.โรงงาน, รอ ผจก.ทั่วไป, รอผู้แจ้งตอบ, รอมอบหมายช่าง, รอช่างเริ่ม, กำลังซ่อม, รอตรวจรับ) พร้อมจำนวนวันที่ค้างเฉลี่ย/นานสุด แตะแถบเพื่อกรองรายการ
- **ต้องลงมือตอนนี้**: ใบค้างเรียงเลยกำหนดเสร็จ → ด่วน → ค้างนานสุด
- **เวลาที่ใช้แต่ละช่วง**: อนุมัติ, รอมอบหมาย, ซ่อม, รอตรวจรับ จากประวัติสถานะ พร้อมเวลาเฉลี่ยแจ้ง → ปิดงาน ปิดงานทันกำหนด และอัตราตรวจรับไม่ผ่าน
- **สองฐานที่ไม่ปนกัน**: งานค้าง/เลยกำหนด/ด่วน/ที่ช่างถืออยู่ นับทุกใบที่ยังไม่จบ ไม่ขึ้นกับช่วงเวลา (ใบเก่าจึงไม่หายไปเมื่อเปลี่ยนช่วง) ส่วนที่เหลือนับตามวันที่แจ้งในช่วงที่เลือก "ยังไม่จบ" ใช้ชุดสถานะเดียวกับ `MNP_REQUEST_CENTER.pendingStatuses("MT_REPAIR")` จึงตรงกับ "ยังไม่จบ N รายการ" ที่หัวโมดูลในขอบเขตสิทธิ์เดียวกัน
- **เลยกำหนดเสร็จ** นับเฉพาะใบที่อยู่ในมือช่าง (รอเริ่มงาน/กำลังซ่อม) ใบที่รอผู้อนุมัติหรือผู้แจ้งไม่นับ ไม่นับฉบับร่างและใบที่ยกเลิก ส่วนใบที่ไม่อนุมัติอยู่ในจำนวนใบแต่ไม่นับเวลา
- **เครื่องจักรที่เสียบ่อย** (Top 10): จำนวนครั้งที่แจ้งซ่อมต่อเครื่องในช่วงที่เลือก นับเฉพาะ**ใบแจ้งซ่อม** ไม่นับใบคำร้อง ใบที่ไม่อนุมัติ ฉบับร่าง และใบที่เลือกเครื่อง "ไม่มี"/"สร้างใหม่" (ไม่ใช่เครื่องจริง แสดงจำนวนที่ไม่นับไว้ใต้กราฟ) เครื่องแยกด้วย แผนกที่แจ้ง + รหัสเครื่อง เพราะรหัสซ้ำข้ามแผนกได้และใบเก็บรหัสเป็นข้อความ ณ วันแจ้ง แตะแถบเพื่อกรองรายการด้านล่าง
- **แผนกที่แจ้งซ่อมบ่อย**: ใบแจ้งซ่อมต่อแผนกที่แจ้ง พร้อมสัดส่วน ยังไม่จบ ด่วน และเวลาปิดงานเฉลี่ย ตารางนี้ไม่ถูกย่อด้วยตัวกรองแผนก (แผนกที่เลือกอยู่ยังเห็นเทียบกับแผนกอื่นได้)
- **ช่างที่ใช้เวลาซ่อมมากสุด**: **ไม่ใช่ชั่วโมงทำงานจริง** เพราะระบบไม่มีช่องบันทึกชั่วโมงทำงาน (`requests`/`request_technicians` ไม่มีฟิลด์ชั่วโมง) ตัวเลขคือเวลาตามนาฬิกาที่ใบอยู่ในสถานะ `in_progress` รวมทุกรอบ (ตรวจรับไม่ผ่านแล้วซ่อมใหม่ก็นับ ใบที่ยังซ่อมอยู่นับถึงเวลาที่เปิดหน้า) ใบที่มีช่างหลายคนนับเต็มเวลาให้ทุกคน และรู้เฉพาะรายชื่อช่างปัจจุบันของใบ (`request_technicians` ไม่เก็บประวัติการเปลี่ยนช่าง) เหมาะเทียบภาระงานคร่าวๆ ไม่ควรใช้คิดค่าแรง หากต้องการชั่วโมงจริง ต้องเพิ่มช่องบันทึกชั่วโมงในฟอร์มบันทึกผลซ่อม (ต้องมี migration และการตัดสินใจเรื่องวิธีกรอก) ส่วน "ถืออยู่" = ใบที่ช่างต้องทำตอนนี้ (รอเริ่มงาน/กำลังซ่อม) นับทุกช่วงเวลา
- ไฟล์: `modules/mt-dashboard-model.js` (นิยามตัวเลขทั้งหมด ไม่มี DOM/Supabase) และ `modules/module-mt-dashboard.js` (โหลดข้อมูลและวาดหน้า) เทสต์ที่ `scripts/tests/mt-dashboard-model.test.mjs` รันด้วย `npm run test:unit`

### ศูนย์คำร้องเดียว (Pilot Web)

- เมนู **คำร้อง** รวมการดูรายการและการสร้างไว้ด้วยกัน หน้าเลือกโมดูลแสดงเฉพาะการ์ดโมดูลและจำนวนงาน ยังไม่โหลดรายการคำร้องหรือแสดงตัวกรอง เมื่อเข้าโมดูลแล้วจึงแสดงรายการ ตัวกรอง และปุ่มสร้างของโมดูลนั้นเพียงจุดเดียว ทางลัดในหน้าหลักเปิดรายการตามประเภทแทนการเปิดฟอร์มทันที
- การ์ด MT / ฝ่ายบริหาร / NCR / IT ใช้กรองรายการและนับงานที่ยังไม่จบตามสิทธิ์หรือขอบเขต **เฉพาะที่ฉันแจ้ง** การเปลี่ยนสถานะคงประเภทและขอบเขตเดิมไว้ ระบบจำประเภทล่าสุดแยกตามบัญชีบนเบราว์เซอร์นั้น และใช้กับลิงก์ `#/requests` ที่ไม่มีตัวกรอง (เช่น **ดูทั้งหมด** ในหน้าหลัก)
- เมนูด้านข้างทุกเมนูพาไปหน้าหลักของเมนูนั้นเสมอ: **คำร้อง** เปิดหน้าเลือกโมดูล (`#/requests?type=all`) ไม่เปิดโมดูลที่จำไว้ ส่วนเมนูอื่นเปิดหน้าแรกโดยไม่มีตัวกรอง กดเมนูของหน้าที่เปิดอยู่จะโหลดหน้านั้นใหม่ ปิดแผง/ตารางที่เปิดค้าง และเลื่อนขึ้นบนสุด (กด Ctrl/⌘ เพื่อเปิดแท็บใหม่ได้ตามปกติ)
- กด **เลือกโมดูล → สร้างคำร้องของโมดูลนั้น → กรอกรายละเอียด** ชื่อโมดูลและปุ่มสร้างระบุประเภทชัดเจน ฟอร์มเปิดตรงกับโมดูลที่กำลังดู เมื่อยกเลิกจะกลับตัวกรองรายการเดิม มีปุ่ม **ย้อนกลับ** (พื้นหลังสีฟ้าเด่นชัด) เพื่อกลับไปเลือกโมดูลอื่น ลิงก์ฟอร์มเดิม `#/new?type=...`, `#/repair/new` และ `#/ncr?new=1` ยังเปลี่ยนเส้นทางเข้าสู่ศูนย์คำร้อง
- กดการ์ดโมดูลแล้วการ์ดทั้งหมดถูกแทนด้วยหัวข้อของโมดูลที่เลือก เนื้อหาซูมเข้าเบา ๆ 320 มิลลิวินาทีและปุ่มสร้างจึงปรากฏ เมนูด้านข้างไม่เคลื่อน การเปลี่ยนสถานะไม่เล่นซ้ำ และข้ามเอฟเฟกต์พร้อมแสดงปุ่มทันทีเมื่อผู้ใช้ตั้ง `prefers-reduced-motion: reduce`
- การ์ดสรุปทั้ง 4 ใบในหน้าหลัก (**งานที่ต้องจัดการ**, **รายการคำร้องของฉัน**, **กำลังดำเนินการ**, **เสร็จแล้ว**) เป็นปุ่มเปิดรายการบนหน้าหลักเลย ไม่เปลี่ยนไปหน้าอื่น รายการแสดงในส่วนเดียวใต้การ์ดสรุปทีละชุด กดการ์ดอื่นเพื่อสลับ กดการ์ดเดิมซ้ำเพื่อซ่อน ส่วนความเคลื่อนไหวล่าสุดและคำร้องแยกตามประเภทยังอยู่ด้านล่าง
  - **งานที่ต้องจัดการ** แสดงขั้นอนุมัติที่รอฉันและงานซ่อมที่ต้องดำเนินการจากข้อมูลชุดเดียวกับตัวเลขบนการ์ด (`getPendingApprovals`, `getMyRepairActionItems`) กดรายการเพื่อเปิดคำร้อง หน้า **รออนุมัติ** ในเมนูยังใช้ได้ตามเดิม
  - อีก 3 การ์ดใช้ query รายการคำร้องเดียวกับศูนย์คำร้อง (`requestListPanel`, RLS เป็นผู้ตัดสินสิทธิ์) กรองตามเงื่อนไขเดียวกับตัวเลข: ผู้แจ้งเป็นฉัน / สถานะ `approved, in_progress` / สถานะ `completed` แต่ละรายการโหลดเมื่อเปิดครั้งแรกของการเปิดหน้าหลักนั้น
  - ลิงก์เก่า `#/requests?status=...` ยังเปิดหน้าเลือกโมดูลพร้อมรายการตามสถานะได้ ส่วน `#/requests?scope=mine&list=1` จะถูกตัด `list` ออกและเปิดหน้าเลือกโมดูลขอบเขตเฉพาะที่ฉันแจ้ง
- ลิงก์และตัวกรองไม่พึ่ง `URLSearchParams.size` จึงใช้ได้กับ Safari ก่อน 17 (iOS 16) และ Chrome ก่อน 113
- NCR ใช้ทะเบียน `ncr_reports` และสถานะของ NCR เดิม กระดานติดตามสถานะองค์กรยังใช้ RPC เดิม ซึ่งคืนคำร้องทั่วไปสูงสุด 500 ใบก่อนกรองประเภท จึงไม่ใช่การค้นย้อนหลังครบทุกใบ
- งานนี้เปลี่ยนการนำทางและตัวกรองของ Pilot Web ตามหน้าที่ใช้งานจริงเท่านั้น ฝั่ง Next.js ยังใช้การนำทางเดิมโดยตั้งใจ ไม่มีการเปลี่ยน RPC, RLS, schema หรือสายอนุมัติ
- ทดสอบ navigation helpers และการนับสถานะด้วย `npm run test:unit` การทดสอบด้วยข้อมูลจำลองไม่ยืนยันการอนุมัติหรือสิทธิ์ฐานข้อมูลจริง

## คำร้องขอเปิดบัญชีและการกู้คืน ID/รหัสผ่าน

พนักงานใหม่ขอเปิดบัญชีได้เองจากหน้า Login แท็บ **ขอเปิดบัญชี** โดยกำหนด ID (รหัสพนักงาน) และรหัสผ่านที่ต้องการ พร้อมเลือกแผนกและระดับตำแหน่ง ระบบยังไม่สร้างบัญชีจริงจนกว่า Admin จะกดอนุมัติ

```text
พนักงานกรอกคำร้อง (ID, รหัสผ่าน, ชื่อ, แผนก, ตำแหน่ง)
   ↓
บันทึกเป็น account_requests สถานะ pending + แจ้งเตือน Admin
   ↓
Admin เปิดหน้า "ผู้ดูแลระบบ" เลือกสิทธิ์ที่จะให้ แล้วกดอนุมัติ
   ↓
สร้าง Supabase Auth user + employees + บันทึก ID/รหัสผ่านลงคลัง
   ↓
พนักงานเข้าสู่ระบบด้วย ID และรหัสผ่านที่ขอไว้ได้ทันที
```

- **แผนก**: RB GR BG PT PK QA ST WH SR FT MT AD ใช้ร่วมกับแผนกเดิม (MGT, IT, HR, PUR, FIN, OPS) ที่ประเภทคำร้องอ้างอิงอยู่ ชื่อภาษาไทยของแผนกใหม่ยังใช้ตัวย่อและแก้ไขได้ภายหลังที่ตาราง `departments`
- **ตำแหน่ง**: รวมเป็น field เดียวกับสิทธิ์เข้าถึงระบบแล้ว (คือ `employees.role_id` ตรงๆ ไม่มี `position_level` แยกต่างหากอีกต่อไป) มีทั้งหมด 7 ตำแหน่งเรียงจากสูงไปต่ำ: ผู้จัดการทั่วไป, ผู้จัดการโรงงาน, ผู้ช่วยผู้จัดการโรงงาน, ผู้จัดการแผนก, ผู้ช่วยผู้จัดการแผนก (ทำแทนผู้จัดการแผนกได้ทุกขั้นตอน เป็นรากฐานสำหรับการเลื่อนตำแหน่ง), พนักงานทั่วไป, ผู้ดูแลระบบ (ลำดับแสดงผลอยู่ที่ `roles.sort_order`) ผู้ยื่นคำร้องขอเปิดบัญชีเลือกตำแหน่งที่ต้องการได้เอง แต่ Admin เป็นผู้เลือกตำแหน่งจริงที่จะให้ตอนกดอนุมัติเสมอ (ช่อง "ตำแหน่งที่ให้" เว้นว่างไว้ = ใช้ตำแหน่งที่ผู้ยื่นขอไว้)
- **บทบาทหลักในการทำงานของผู้ดูแลระบบ** (`employees.acting_role_id`): บัญชี Admin ที่ทำงานจริงในตำแหน่งอื่นด้วย (เช่น ผู้จัดการทั่วไปที่ต้องใช้สิทธิ์ Admin) ให้ผู้ดูแลระบบตั้งได้ที่หน้า "ผู้ดูแลระบบ" → แท็บ ID/รหัสผ่าน → "แก้ไข" บัญชีนั้น → ช่อง "บทบาทหลักในการทำงาน" (ใช้ได้เฉพาะบัญชีตำแหน่งผู้ดูแลระบบ ตารางบัญชีแสดงบทบาทที่ตั้งไว้ใต้ตำแหน่ง; Next.js ยังไม่มีหน้าแก้ไขบัญชีจึงตั้งได้จาก Pilot Web เท่านั้น) เมื่อตั้งแล้ว ระบบถือว่าบัญชีนี้ถือบทบาทนั้นในเรื่องสายอนุมัติและการแจ้งเตือน: นับเป็นผู้ถือบทบาทตอนสร้างสาย ผจก.โรงงาน → ผจก.ทั่วไป, ได้แจ้งเตือน "มีคำร้องรออนุมัติ" ของขั้นที่ผูกกับบทบาทนั้น (ยังต้องมีสิทธิ์โมดูล) และหน้า "รออนุมัติ" แสดงเฉพาะขั้นของบทบาทนั้น แต่จะไม่ได้แจ้งเตือนคำร้องเปิดบัญชี/แก้ไข ID (ยังจัดการได้ที่หน้า Admin) สิทธิ์ Admin อื่นไม่เปลี่ยน เลือก "ผู้ดูแลระบบ" เพื่อกลับเป็นแบบเดิม ค่านี้ถูกล้างเองเมื่อบัญชีถูกเปลี่ยนออกจาก Admin และ NCR ยังตรวจตำแหน่งจริงเสมอ (ดู `20261003010000_admin_acting_role.sql` และ `20261003020000_admin_sets_acting_role.sql`)
- **ขอแก้ไข ID/รหัสผ่าน**: ผู้ใช้ที่มีบัญชีแล้วส่งคำร้องได้จากหน้า "ข้อมูลส่วนตัว" รหัสผ่านเดิมยังใช้ได้จนกว่า Admin จะอนุมัติ ส่วนบัญชีที่มีสิทธิ์ `accounts.manage` เป็นผู้อนุมัติอยู่แล้ว หน้าเดียวกันจึงบันทึกและอนุมัติให้ทันทีในขั้นตอนเดียว โดยยังเดินผ่าน RPC ชุดเดิมและบันทึกประวัติไว้ครบ
- **บัญชีผู้ดูแลระบบ**: คลัง ID/รหัสผ่านแสดงพนักงานทุกบัญชีรวมถึงบัญชี Admin และบัญชีของผู้ที่กำลังเปิดดูเอง แถวของตนเองมีป้าย "บัญชีของคุณ"
- **Admin แก้ไขบัญชีได้ทุกคน**: กด "แก้ไข" ที่แถวใดก็ได้ในคลัง จะเปิดฟอร์มที่แก้ได้ทุกช่อง — ID, ชื่อ-สกุล, อีเมล, เบอร์, ชื่อตำแหน่งงาน, แผนก, ตำแหน่ง, สถานะใช้งาน และตั้งรหัสผ่านใหม่ให้ผู้ที่ลืมได้ในฟอร์มเดียวกัน
- **ออกจากระบบทันทีหลังแก้ ID/รหัสผ่านของตัวเอง**: ไม่ว่าจะแก้ผ่านการ์ด "แก้ไข ID / รหัสผ่านของฉัน" ในหน้าข้อมูลส่วนตัว หรือ Admin แก้บัญชีของตัวเองจากคลัง ถ้า ID หรือรหัสผ่านของบัญชีที่ล็อกอินอยู่เปลี่ยน ระบบจะเรียก `forceReLogin` ให้ออกจากระบบทันทีและต้องเข้าสู่ระบบใหม่ด้วยข้อมูลล่าสุดเสมอ
- **ผู้ใช้ทั่วไปแก้ข้อมูลตัวเอง**: หน้า "ข้อมูลส่วนตัว" แก้ชื่อ-สกุล อีเมล เบอร์ และชื่อตำแหน่งงานได้เอง ส่วนแผนกและตำแหน่งเป็นตัวกำหนดสิทธิ์และเส้นทางอนุมัติ จึงล็อกไว้ให้ Admin เป็นผู้แก้ ป้องกันไม่ให้ผู้ใช้ยกระดับสิทธิ์ของตนเอง
- **กันล็อกเอาต์**: `app_admin_update_employee` ไม่ยอมให้ผู้ดูแลระบบถอดสิทธิ์ `accounts.manage` หรือปิดบัญชีของตนเอง (`CANNOT_DEMOTE_SELF`) เพื่อไม่ให้เหลือระบบที่ไม่มีใครเข้าไปแก้ไขได้
- **คลัง ID/รหัสผ่าน**: `account_credentials` เก็บ ID และรหัสผ่านที่ออกให้ เพื่อให้ Admin ค้นคืนได้เมื่อผู้ใช้ลืม

### การป้องกันคลังรหัสผ่าน

`account_requests` และ `account_credentials` ถูกปิดการเข้าถึงตรงทั้งหมด ไม่มี grant ให้ `anon`/`authenticated` และมี deny-all RLS policy กำกับ การอ่านทำได้เฉพาะผ่าน RPC ที่ตรวจสิทธิ์ `accounts.manage`

| RPC | ผู้เรียกได้ | หน้าที่ |
|---|---|---|
| `app_request_credential_change` | ผู้ใช้ที่ล็อกอิน | ขอแก้ไข ID/รหัสผ่านของตนเอง |
| `app_list_account_requests` | Admin | รายการคำร้อง โดยไม่คืนค่ารหัสผ่าน |
| `app_apply_account_request` | Admin | อนุมัติ สร้างพนักงาน/สิทธิ์ และบันทึกลงคลัง |
| `app_reject_account_request` | Admin | ไม่อนุมัติ พร้อมล้างรหัสผ่านที่แนบมา |
| `app_list_credentials` | Admin | รายชื่อและสถานะรหัสผ่าน (ปิดค่าไว้) |
| `app_reveal_credential` | Admin | เปิดดูรหัสผ่านรายคน และบันทึก audit ทุกครั้ง |
| `app_admin_update_employee` | Admin | แก้ไขข้อมูลพนักงานคนใดก็ได้ทุกช่อง รวมบทบาทและสถานะใช้งาน |
| `app_admin_target_auth_user` | Admin | ตรวจสิทธิ์และคืนบัญชี auth ของเป้าหมายก่อนเปลี่ยนรหัสผ่าน |
| `app_admin_record_password` | Admin | บันทึกรหัสผ่านที่ Admin ตั้งให้ลงคลัง พร้อม audit |
| `app_update_own_profile` | ผู้ใช้ที่ล็อกอิน | แก้ชื่อ อีเมล เบอร์ และชื่อตำแหน่งงานของตนเอง |

หน้าคลังแสดงรหัสผ่านเป็น `••••••••` จนกว่าจะกดปุ่มแสดง ซึ่งเรียก `app_reveal_credential` และเขียน `audit_logs` ด้วย action `REVEAL_CREDENTIAL` พร้อมผู้กดและเวลา

ข้อจำกัดที่ต้องทราบ: บัญชีที่สร้างก่อนระบบนี้จะยังไม่มีรหัสผ่านในคลัง เพราะ Supabase Auth เก็บเป็น hash และย้อนกลับไม่ได้ ผู้ใช้ต้องส่งคำร้องขอแก้ไขรหัสผ่านหนึ่งครั้งก่อน คลังจึงจะมีค่าให้กู้คืน และหากผู้ใช้เปลี่ยนรหัสผ่านด้วยช่องทางอื่นนอกเหนือจากคำร้องนี้ ค่าในคลังจะไม่ตรงกับรหัสผ่านจริง

### หน้าคำร้องใช้ RLS ตัดสินอย่างเดียว ไม่กรองซ้ำฝั่ง client

เดิมหน้าคำร้องและหน้าหลักบังคับ `.eq("requester_id", ตัวเอง)` กับทุกบทบาทที่ไม่ใช่
admin / `requests.view_all` / `requests.operate` ผลคือ **หัวหน้าแผนกซ่อมบำรุงและช่าง
เปิดหน้าคำร้องแล้วว่างเปล่า** ทั้งที่มีใบรออนุมัติจากตัวเองค้างอยู่ และมีงานที่ตัวเอง
เป็นช่างผู้รับผิดชอบ เพราะใบเหล่านั้นไม่ได้มี `requester_id` เป็นตัวเอง

ตอนนี้ตัดการกรองซ้ำออก ให้ RLS เป็นตัวตัดสินชั้นเดียว แล้วเพิ่มปุ่มสลับขอบเขตแทน

| ปุ่ม | ลิงก์ | เห็นอะไร |
| --- | --- | --- |
| ทุกใบที่เกี่ยวข้องกับฉัน (ค่าเริ่มต้น) | `#/requests` | ใบที่แจ้งเอง + รออนุมัติจากเรา + เป็นผู้รับผิดชอบ + งานของแผนกที่เรารับผิดชอบ |
| เฉพาะที่ฉันแจ้ง | `#/requests?scope=mine` | พฤติกรรมเดิม คือเฉพาะใบที่ตัวเองเป็นผู้แจ้ง |

มุมมองเริ่มต้นเพิ่มคอลัมน์ "ผู้แจ้ง" ด้วย เพราะตอนนี้มีใบของคนอื่นปนอยู่แล้ว

## กระดานติดตามสถานะ — ทุกคนเห็นว่าแต่ละใบไปถึงไหนแล้ว

หน้า **คำร้อง** มีสองมุมมอง สลับได้ที่แท็บด้านบนของหน้า

| มุมมอง | ลิงก์ | เห็นอะไร |
| --- | --- | --- |
| รายการตามสิทธิ์ | `#/requests` | รายการเดิมตาม RLS (ใบของตัวเอง ใบที่ตนรับผิดชอบ ใบที่ตนอนุมัติ หรือทุกใบถ้ามีสิทธิ์ `requests.view_all` / `requests.operate`) เพิ่มคอลัมน์ "ความคืบหน้า" |
| ติดตามสถานะทุกใบ | `#/requests?view=board` | พนักงานที่ยัง active **ทุกคน** เห็นทุกใบว่าเดินไปถึงขั้นไหนแล้ว |

กระดานนี้ไม่ได้แก้ RLS ของตารางไหนเลย แต่อ่านผ่าน RPC `public.app_request_status_board(p_status, p_search, p_limit)`
ซึ่งเป็น `security definer` และคืนเฉพาะฟิลด์ระดับติดตามสถานะ

- **คืน**: เลขที่ใบ · ประเภท · แผนกที่แจ้ง · รหัส/ชื่อเครื่องจักร · ผู้แจ้ง · ช่างผู้รับผิดชอบ · สถานะ · ขั้นอนุมัติปัจจุบัน · คนที่ต้องดำเนินการต่อ · วันที่ · ธงด่วน
- **ไม่คืน**: `description` และ `details` (รายละเอียดอาการ) · ไฟล์แนบ · ความเห็นผู้อนุมัติ · ผลวิเคราะห์สาเหตุ/อะไหล่ · หมายเหตุการตรวจรับ
- ใบแจ้งซ่อมคืน `subject` เป็นรหัส/ชื่อเครื่องจักร ไม่ใช่ `title` เพราะ `app_create_repair_request` ประกอบ title จาก
  `"<ชื่อเครื่องจักร> — <รายละเอียดอาการ>"` การส่ง title ออกไปจึงเท่ากับส่งรายละเอียดอาการออกไปด้วย
- `can_open` บอกว่าบัญชีที่เรียกมีสิทธิ์เปิดดูรายละเอียดเต็มของใบนั้นหรือไม่ UI ทำเป็นลิงก์เฉพาะใบที่ `true`
  ส่วนการบังคับสิทธิ์จริงยังเป็น RLS ในหน้ารายละเอียด (`#/request?id=…`) เหมือนเดิม
- `anon` เรียกไม่ได้ และบัญชีที่ยังไม่ได้ผูกกับ `employees` ที่ active จะได้ `EMPLOYEE_NOT_FOUND`

แถบความคืบหน้าใช้สถานะปัจจุบันของใบเป็นตัวตั้ง ใบแจ้งซ่อมมี 6 ขั้น
(รออนุมัติ → รอมอบหมายช่าง → รอช่างเริ่มงาน → กำลังซ่อม → รอตรวจรับ → เสร็จแล้ว)
คำร้องทั่วไปมี 4 ขั้น (รออนุมัติ → อนุมัติแล้ว → กำลังดำเนินการ → เสร็จแล้ว)
ส่วน `more_info` / `rejected` / `cancelled` แสดงเป็นจุด "ติดขัด" ค้างที่ขั้นอนุมัติ
การตรวจรับไม่ผ่านจะย้อนใบกลับไป `assigned` แถบจึงถอยตามด้วย ไม่ค้างที่ขั้นสูงสุดที่เคยผ่าน

## สิทธิ์อนุมัติแยกตามโมดูล

เดิมใครก็ตามที่ถือบทบาทผู้อนุมัติของแผนกเจ้าของประเภทคำร้อง (เช่น หัวหน้างานแผนก MT) จะอนุมัติได้ทุกโมดูลที่แผนกตนรับผิดชอบทันที หน้า "ผู้ดูแลระบบ" แท็บ **สิทธิ์อนุมัติตามโมดูล** ให้ Admin กำหนดเพิ่มอีกชั้นว่าผู้อนุมัติแต่ละคนอนุมัติโมดูลไหนได้บ้าง (เช่น ใบคำร้อง/แจ้งซ่อม MT, ใบคำร้องถึงฝ่ายบริหาร) โดยติ๊ก/ถอดติ๊กเป็นรายบุคคล×โมดูล ผู้ที่ยังไม่ถูกติ๊กโมดูลใดจะไม่เห็นและอนุมัติคำร้องโมดูลนั้นแม้อยู่แผนกและถือบทบาทผู้อนุมัติเดียวกันก็ตาม

- **ไม่กระทบขั้นตอนหัวหน้าแผนก**: ขั้น "หัวหน้าแผนก" ผูกกับตัวบุคคล (`approver_employee_id`) ไม่ใช่บทบาท จึงไม่ถูกจำกัดด้วยตารางนี้ หัวหน้าแผนกยังอนุมัติคำร้องของลูกน้องตนเองได้ตามปกติทุกโมดูล
- **ยังคงพฤติกรรมเดิมทันทีหลัง migrate**: ผู้อนุมัติที่มีอยู่แล้ววันนี้ถูกให้สิทธิ์ทุกโมดูลที่ตนอนุมัติอยู่แล้วโดยอัตโนมัติในไฟล์ migration จากนี้ไป Admin เป็นผู้ให้/ถอดสิทธิ์ผู้อนุมัติคนใหม่เอง
- **Admin ไม่ถูกจำกัด**: บัญชีที่มีสิทธิ์ `requests.view_all` (Admin) มองเห็นและอนุมัติได้ทุกคำร้องเสมอ ไม่ต้องมีแถวสิทธิ์ในตารางนี้ และจะไม่ปรากฏในตารางจัดการเพื่อไม่ให้สับสน
- **บังคับทั้งฝั่งมองเห็นและฝั่งกดอนุมัติ**: `private.can_access_request` (ใช้ใน RLS ของ requests/approval_steps/comments/attachments) และ `app_approval_decision` ตรวจสิทธิ์โมดูลเหมือนกัน ผู้ที่ไม่มีสิทธิ์จะไม่เห็นคำร้องนั้นเลย ไม่ใช่แค่กดอนุมัติไม่ได้

`approval_module_permissions` ปิดการเข้าถึงตรงทั้งหมดเหมือน `account_requests`/`account_credentials` เข้าถึงได้เฉพาะผ่าน RPC ที่ตรวจสิทธิ์ `approvals.manage`

| RPC | ผู้เรียกได้ | หน้าที่ |
|---|---|---|
| `app_list_module_permissions` | Admin | ตารางสิทธิ์ของผู้อนุมัติทุกคน × ทุกโมดูล พร้อมสถานะให้สิทธิ์แล้วหรือยัง |
| `app_set_module_permission` | Admin | ให้/ถอดสิทธิ์อนุมัติโมดูลหนึ่งของพนักงานคนหนึ่ง |
| `app_my_approval_modules` | ผู้ใช้ที่ล็อกอิน | ดูรายการโมดูลที่ตนเองอนุมัติได้ ใช้กรองหน้า "รออนุมัติ" ฝั่งไคลเอนต์ |

## เส้นทางใบแจ้งซ่อม

ใบแจ้งซ่อมหนึ่งใบเดินเป็นเส้นเดียว ตั้งแต่ผู้แจ้งเปิดใบ ผ่านการอนุมัติสองชั้น ไปถึงช่าง แล้วกลับมาจบ
ที่ผู้แจ้งเป็นคนตรวจรับ มีทางย้อนกลับสองเส้นเท่านั้นคือ "ขอข้อมูลเพิ่มเติม" และ "ตรวจรับไม่ผ่าน"

```text
ผู้แจ้งเปิดใบ
   ↓
ผู้จัดการโรงงานอนุมัติ ───── ไม่อนุมัติ → จบใบ
   ↓                    └── ขอข้อมูลเพิ่ม → ผู้แจ้งตอบกลับ → กลับมาขั้นเดิม
ผู้จัดการทั่วไปอนุมัติ ────── (สองทางเดียวกัน)
   ↓
ผู้จัดการแผนกซ่อมบำรุงมอบหมายช่าง   ← ไม่ใช่ขั้นอนุมัติ เป็นการแจกจ่ายงาน
   ↓
ช่างที่ถูกมอบหมายกดเริ่มงาน
   ↓                    (ระหว่างทาง: กดหมุดความคืบหน้าถ้าแนวทางที่เลือกต้องรอของ)
ช่างบันทึกผลซ่อม
   ↓
ผู้แจ้งตรวจรับ ── ผ่าน → ปิดงาน
             └── ไม่ผ่าน → กลับไปหาช่างชุดเดิม (ไม่ต้องขออนุมัติใหม่)
```

### สถานะและคนที่ต้องขยับต่อ

| สถานะ | คีย์ในระบบ | ลูกอยู่ในมือใคร |
| --- | --- | --- |
| รออนุมัติ (ผจก.โรงงาน) | `pending_approval` + `current_step` = 1 | ผู้จัดการโรงงาน |
| รออนุมัติ (ผจก.ทั่วไป) | `pending_approval` + `current_step` = 2 | ผู้จัดการทั่วไป |
| ต้องการข้อมูลเพิ่มเติม | `more_info` | ผู้แจ้งซ่อม |
| รอมอบหมายช่าง | `pending_assign` | ผจก.แผนกซ่อมบำรุง |
| รอดำเนินการ | `assigned` | ช่างผู้รับผิดชอบ |
| กำลังซ่อม | `in_progress` | ช่างผู้รับผิดชอบ |
| รอผู้แจ้งตรวจสอบผลการซ่อม | `pending_verify` | ผู้แจ้งซ่อม |
| ซ่อมเรียบร้อย | `completed` | — ปิดงานแล้ว |
| ไม่อนุมัติ | `rejected` | — จบใบแล้ว |

ระบบเดิมแยกเป็น `PENDING_FM`/`PENDING_GM` และ `NEEDS_INFO_FM`/`NEEDS_INFO_GM` คนละคีย์ ที่นี่เก็บเป็น
คีย์เดียวแล้วดู `current_step` ประกอบ หน้ารายละเอียดจึงเติมชื่อขั้นต่อท้ายป้ายสถานะให้เอง
(`repairStatusBadge` ใน `app.js`) เช่น "รออนุมัติ (ผจก.โรงงาน)" เพื่อให้อ่านได้เหมือนกัน

### หมุดความคืบหน้า

สร้างอัตโนมัติตอนมอบหมาย ตามแนวทางที่ ผจก.ซ่อมบำรุงเลือก — เฉพาะทางที่ "ต้องรอของ" เท่านั้นที่มีหมุด

| เลือกไว้ว่า | หมุดที่ได้ |
| --- | --- |
| การดำเนินงาน = ต้องการสั่งซื้ออุปกรณ์ · หรือ ความเห็น = ซื้ออุปกรณ์มาทำเอง | สั่งซื้ออุปกรณ์เรียบร้อย → ของมาส่งเรียบร้อย |
| ความเห็น = ส่งซ่อม | ส่งออกไปซ่อมเรียบร้อย → รับกลับจากร้านซ่อมเรียบร้อย |
| ความเห็น = เรียกช่างภายนอกมาซ่อม | นัดหมายช่างภายนอกเรียบร้อย → ช่างภายนอกเข้าหน้างานเรียบร้อย |

หมุดไม่บล็อกการกดเริ่มซ่อมหรือจบงาน เป็นการรายงานความคืบหน้าอย่างเดียว เก็บวันที่ที่กด ผู้กด และ

ยังไม่ได้เลื่อนวันที่ใหม่) ระบบส่งอีเมลถามช่างในชุด + ผจก.ซ่อมบำรุงเจ้าของงานว่า "ของที่สั่งซื้อมาส่ง
หรือยัง" กันลืมกดบันทึก — ดูหัวข้อ "อีเมลเตือนของมาส่งหรือยัง (pg_cron)" ในหมวดแจ้งเตือนทางอีเมล

### กฎที่ทำให้เส้นทางนี้ไม่หลุด

- **อนุมัติครบสองชั้นเท่านั้นถึงจะถึงมือช่าง** ไม่มีทางลัด และผู้อนุมัติกดได้เฉพาะขั้นของตัวเอง —
  `app_approval_decision` ตรวจว่า step ยัง `pending` และตรงกับ `current_step` ของใบเสมอ
- **"ขอข้อมูลเพิ่มเติม" ไม่ใช่การรีเซ็ตใบ** เมื่อผู้แจ้งตอบกลับ ใบกลับไปที่ขั้นเดิมของคนที่ขอ ไม่ได้
  ย้อนไปเริ่มอนุมัติใหม่ และคำตอบถูกต่อท้ายความเห็นเดิมในขั้นนั้น
- **ข้อความของแต่ละคนอยู่ใน "ลำดับเหตุการณ์" ทุกรอบ** เหตุผลที่ขอข้อมูลเพิ่ม คำตอบของผู้แจ้ง เหตุผลที่ไม่อนุมัติ
  และความเห็นตอนอนุมัติขั้นสุดท้าย ถูกเก็บเป็น `request_status_history.note` ของการเปลี่ยนสถานะครั้งนั้น
  (RPC ฝากข้อความผ่าน `private.set_status_note` ให้ trigger ใน transaction เดียวกัน) เพราะ
  `approval_steps.comment` ถูกเขียนทับทุกรอบที่ขอ-ตอบกัน แถวเก่าถูกเติมย้อนหลังจาก `audit_logs`
  (`20261005020000_status_history_person_notes.sql`) หน้าคำร้องแสดงข้อความเป็นกล่องแยกใต้แต่ละเหตุการณ์
- **ตรวจรับไม่ผ่านย้อนได้ไม่จำกัดรอบ** ทุกครั้งเก็บลง `request_verifications` ใบวนอยู่ระหว่าง
  `assigned` ↔ `pending_verify` จนกว่าผู้แจ้งจะกดผ่าน
- **เปลี่ยนช่างได้ตลอดทาง** ยกเว้นใบที่ถูกปฏิเสธไปแล้ว
- **ทุกการเปลี่ยนสถานะถูกบันทึกเป็นลำดับเหตุการณ์** พร้อมเวลา ผู้ทำ และหมายเหตุ และทุก RPC เป็น
  transaction เดียว ล้มกลางคันแล้วย้อนกลับทั้งชุด ไม่ทิ้งข้อมูลครึ่งใบ

## ใบคำร้องถึงฝ่ายบริหาร (PP01-FM08)

  รายการที่ยกเลิกไม่ถูกลบ เก็บผู้ยกเลิกและเหตุผลไว้ ทุกขั้นบันทึกใน `ncr_status_history` และ `audit_logs`
- **แจ้งเตือน**: ทุกขั้นแจ้งผู้ที่ต้องทำขั้นถัดไปผ่าน `notifications` (ลิงก์ `/ncr/<id>`) ซึ่งเข้าคิวอีเมลเดิม
  ต้อง deploy `notify-email` ใหม่เพื่อให้ลิงก์ในอีเมลเปิดหน้า NCR ตรง
- **แดชบอร์ด NCR** (`#/ncr-dashboard`, `modules/module-ncr-dashboard.js` + `modules/ncr-dashboard-model.js`): เปิดจากปุ่ม **แดชบอร์ด NCR** ที่หัวหน้า NCR
  อ่านผ่าน RLS เดียวกับทะเบียน (แต่ละคนเห็นเฉพาะ NCR ที่มีสิทธิ์) ไม่นับใบที่ยกเลิกและรายการความสูญเสียที่ยกเลิก ตัวกรองอยู่ใน URL
  จึงแชร์ลิงก์มุมมองเดียวกันได้ รายละเอียดการ์ดและนิยามตัวเลขดูหัวข้อ "NCR: ต้นทุนความสูญเสีย ผลดำเนินการ และแดชบอร์ด" ด้านบน
- **ยังไม่มีใน Phase 1**: ออก CAR จาก NCR (Phase 2), นำเข้า NCR LOG 2026 เดิม และตารางต้นทุนมาตรฐาน

## โหมดทดสอบสำหรับผู้ดูแลระบบ (Admin Sandbox) — เริ่มที่ NCR

ให้ admin ลองใช้ระบบตามบทบาทต่างๆ ครบทุกขั้นบนฐานข้อมูลเดียวกับของจริง โดยข้อมูลทดสอบ **แยกที่ฐานข้อมูล** (migration `20261005030000_admin_sandbox_mode.sql`)

**วิธีใช้ (เฉพาะ admin):** `#/admin` → แท็บ **ทดสอบระบบ** → กด **เข้าโหมดทดสอบ** ที่บัญชีทดสอบที่ต้องการ (เช่น พนักงาน RB, ผจก.โรงงาน, ผจก. QA)
ระบบพาไปทะเบียน NCR และแสดงแถบสีเหลืองทุกหน้า เลือก "ทำหน้าที่เป็น" เพื่อสลับบทบาทระหว่างขั้นตอน (ออกใบ → พิจารณา → ตอบ → ติดตาม → ลงนาม 3 ขั้น → ยกเลิก → ความสูญเสีย)
**ล้างข้อมูลทดสอบ** ลบใบทดสอบทั้งหมดและเริ่มนับ `TEST-QA001/yy` ใหม่ และ **ออกจากโหมดทดสอบ** กลับไปใช้งานจริง (ผู้ใช้ที่ไม่ใช่ admin ไม่เห็นแท็บนี้ และ RPC `app_sandbox_*` ปฏิเสธด้วย `NOT_AUTHORIZED`)

**ทำงานอย่างไร**

| เรื่อง | กลไก |
| --- | --- |
| บัญชีทดสอบ | แถว `employees` ที่ `is_test = true` ต้อง **inactive และไม่มี `auth_user_id`** (CHECK constraint) ล็อกอินไม่ได้ และฟังก์ชันเดิมที่เลือกผู้อนุมัติ/ผู้รับแจ้งเตือนจะข้ามไปเอง 18 บัญชี `SBX-*` (9 บัญชีครบบทบาทที่ NCR ใช้ + พนักงานขาย SA, พนักงานวางแผน PP ของใบสั่งผลิต, พนักงาน ST ของใบสั่งวัตถุดิบ, พนักงาน SR GR PT BG WH ของสายผลิต และผู้ช่วย ผจก.โรงงาน `SBX-FT-AFM` ของตารางการผลิต) ซ่อนจากรายการบัญชีของ admin (`app_list_credentials`) |
| การสลับบทบาท | `sandbox_sessions` (หนึ่งแถวต่อ admin) ระหว่างอยู่ในโหมด `private.ncr_current_employee()` คืนบัญชีทดสอบแทน admin ทุก RPC ของ NCR จึงตรวจสิทธิ์ตามบทบาท/แผนกของบัญชีนั้น และตรวจซ้ำทุกครั้งว่ายังเป็น admin (ถ้าถูกลดสิทธิ์ โหมดทดสอบหยุดทันที) |
| แยกข้อมูล | `ncr_reports.is_test` กำหนดโดย trigger จากโหมดของผู้ออกใบ (ไม่รับจาก client) ใบทดสอบเห็น/แก้ได้เฉพาะในโหมดทดสอบ ใบจริงเห็น/แก้ได้เฉพาะนอกโหมดทดสอบ รวมถึง admin เอง ฝ่าฝืน = `SANDBOX_SCOPE_MISMATCH` (RLS, ทะเบียน และแดชบอร์ดแยกตามนี้ด้วย) |
| เลขที่เอกสาร | ตัวนับแยก `NCR-TEST` เลขขึ้นต้น `TEST-QA…` ตัวนับจริง (`QA041/26` …) ไม่ขยับ |
| แจ้งเตือน/อีเมล/ตัวเตือนงานค้าง | `private.ncr_audience()` ไม่คืนผู้รับสำหรับใบทดสอบ จึงไม่มีแจ้งเตือน อีเมล หรือเตือนงานค้างถึงใครเลย |
| ด่าน fail-closed | ระหว่างอยู่ในโหมดทดสอบ การเขียนตารางที่ยังไม่รู้จักโหมดทดสอบ (`requests`, `employees`, `notifications` ฯลฯ) ถูกปฏิเสธด้วย `SANDBOX_MODULE_UNSUPPORTED` กันลืมออกจากโหมดแล้วสร้างข้อมูลจริง หน้าเว็บซ่อนเมนูของโมดูลอื่นและพากลับ NCR |

**ข้อจำกัด:** บันทึกข้อมูลได้เฉพาะ NCR และ Item master ของฝ่ายโรงงาน (ดูหัวข้อด้านล่าง) · แนบไฟล์ในโหมดทดสอบไม่ได้ (ลบไฟล์ใน Storage ด้วย SQL ไม่ได้ จึงไม่ปล่อยให้เกิดไฟล์ค้าง) ·
`audit_logs` ยังบันทึกการกระทำในโหมดทดสอบ (ผู้กระทำคือบัญชี admin จริง) เพื่อตรวจย้อนหลัง · `has_permission()` ยังมองเป็นบัญชี admin จริง ·
แดชบอร์ด NCR เก็บแคช 1 นาทีต่อบัญชี หลังล้างข้อมูลทดสอบตัวเลขอาจค้างได้ชั่วครู่

**เพิ่มโมดูลใหม่ในอนาคต:** `admin_sandbox_mode.test.sql` ตรวจว่าทุกตารางใน `public` อยู่ใน `private.sandbox_unguarded_tables()` (รู้จักโหมดทดสอบแล้ว) หรือมี trigger `sandbox_guard` มิฉะนั้นไม่ผ่านใน CI
ตารางของโมดูลใหม่จึงปลอดภัยโดยปริยาย (เขียนไม่ได้ระหว่างโหมดทดสอบ) ถ้าจะให้โมดูลนั้นรองรับโหมดทดสอบ ต้องทำให้ครบ 5 ข้อ แล้วค่อยประกาศ `sandbox: true` ในไฟล์โมดูลของ Pilot Web (`modules/module-<x>.js`) และเพิ่มชื่อตารางใน `private.sandbox_unguarded_tables()` ผ่าน migration ใหม่:
1. ตารางหลักมีคอลัมน์ `is_test` ที่ trigger กำหนดจากโหมดของผู้ทำรายการ และ RLS/ฟังก์ชันอ่านเทียบโหมดเดียวกัน
2. ผู้ทำรายการของ RPC มาจากตัวช่วยที่รู้จักบัญชีทดสอบ (แบบ `private.ncr_current_employee()`)
3. ตัวนับเลขเอกสารแยกชุดสำหรับใบทดสอบ
4. ผู้รับแจ้งเตือนและตัวเตือนงานค้างไม่รวมข้อมูลทดสอบ
5. มีบัญชีทดสอบ (`is_test`) ครบบทบาทที่โมดูลต้องใช้ และมี pgTAP ทั้งกรณีอนุญาตและปฏิเสธ

**Rollback:** ดูหัวไฟล์ migration (ลบใบทดสอบก่อน แล้ว drop trigger/ฟังก์ชัน/ตาราง/คอลัมน์ที่เพิ่ม และนำนิยามฟังก์ชันเดิมของ `20261002020000`/`20261005010000`/`20261001030000` กลับ) ไม่มีข้อมูลจริงถูกแก้
**ลำดับ deploy:** `npx supabase db push` ก่อนแล้วค่อย deploy Pilot Web (ถ้าฐานข้อมูลยังไม่อัปเดต แท็บ "ทดสอบระบบ" จะบอกให้ push และ admin ใช้งานส่วนอื่นได้ตามปกติ)

### โมดูลฝ่ายโรงงาน (โหมดทดสอบ)

เมนูข้าง **ฝ่ายโรงงาน** (`#/factory`) โผล่เฉพาะในโหมดทดสอบ ข้างเมนู NCR/CAR มี 6 แผนก เรียงตามนี้: **PP** วางแผนการผลิต · **RB** ขึ้นรูปยาง · **GR** แปรรูปยาง · **PT** ขึ้นรูปพลาสติก · **BG** เย็บจักร · **PK** ประกอบบรรจุภัณฑ์ กดการ์ดแผนกเพื่อเปิดหน้าแผนก (`#/factory?dept=<รหัส>`) และสลับแผนกจากแท็บด้านบนได้

- **Item master** เป็นเมนูย่อยในแถบข้างซ้าย **ใต้เมนู "ฝ่ายโรงงาน"** เมื่อเลือกฝ่ายโรงงานอยู่ (หน้ารวม หน้าแผนก หรือหน้ารายการ) จะมี dropdown **Item master** โผล่ใต้เมนู กดเปิดแล้วเห็นโครงสร้างต้นไม้ตามภาพเมนู ERP ที่ผู้ใช้ส่งมา กดโฟลเดอร์เพื่อกางรายการ (เบราว์เซอร์ที่รองรับ `<details name>` กางได้ทีละโฟลเดอร์) กดรายการเพื่อเปิด `#/factory?item=<key>`
  - **สถานะเปิด/ปิดมาจาก URL**: แถบข้างถูกวาดใหม่ทุกครั้งที่เปลี่ยนหน้า เมนูย่อยจึงเปิดค้างพร้อมโฟลเดอร์และรายการที่เลือกเมื่อ URL มี `item` ที่รู้จัก ถ้าไม่มีจะหุบ ค่า `item` ที่ไม่รู้จักพากลับหน้ารวม ถ้าส่ง `item` พร้อม `dept` รายการมาก่อน โมดูลประกาศเมนูย่อยผ่าน `nav[].subnav(active)` ที่ `app.js` (`requestModuleNavLinks`) ลิงก์ในเมนูย่อยต้องอยู่ใน `.nav-sub` เพื่อให้ลิ้นชักมือถือปิดเองและโหลดหน้าใหม่ตามกติกาของ `bindShell`
  - **ความกว้างจอ**: จอกว้าง (เกิน 1040px) แสดงเมนูย่อยในแถบข้าง และแถบข้างเลื่อนได้เมื่อรายการยาวกว่าจอ ปุ่มผู้ใช้ท้ายแถบยังเห็น จอมือถือ (ไม่เกิน 760px) อยู่ในลิ้นชักเมนู จอ 761–1040px แถบข้างหุบเหลือแต่ไอคอน จึงซ่อนเมนูย่อยและแสดงการ์ด Item master ในหน้าแทน (ต้นไม้ชุดเดียวกัน ซ่อน/แสดงด้วย media query)
  - ทุก dropdown/ต้นไม้ใช้ `<details>` และ `<select>` ของเบราว์เซอร์ จึงแตะบน iPhone และใช้คีย์บอร์ดได้โดยไม่ต้องมีโค้ดปิด popup (ถ้าวันหน้าเปลี่ยนเป็น popup ลอยหรือ combobox ต้องใช้ `data-popup` และ `closePopup` ตามกติกา)

- **ฐานข้อมูล**: 14 ตาราง `factory_*` (ตัด `app_meta` ของแอปเดิมออก เพราะการเติมข้อมูลตรวจว่ามี Item ทดสอบแล้วหรือยัง) จำนวนใช้ `numeric` แทน REAL หน่วยนับ 4 หน่วยและหมวดหมู่ 9 หมวดใส่ใน migration เป็นข้อมูลอ้างอิงร่วม ทุกตารางปิดเข้าถึงตรง (RLS deny-all + ถอนสิทธิ์ anon/authenticated) อ่าน/เขียนผ่าน RPC เท่านั้น: `app_factory_master_data` (อ่านทั้งชุด), `app_factory_save_item` (เพิ่ม/แก้ไข), `app_sandbox_seed_factory` / `app_sandbox_purge_factory` (เติม/ล้างข้อมูลทดสอบ)
- **กติกาของ Item ที่คงจากแอปเดิม**: รหัส 2–40 ตัว (อังกฤษ ตัวเลข `-` `_` ระบบแปลงเป็นตัวพิมพ์ใหญ่) ไม่ซ้ำ, ประเภท หน่วยนับฐาน และการติดตามล็อตล็อกหลังสร้าง (`ITEM_LOCKED_FIELDS`), ไม่มีการลบ ใช้สถานะหยุดใช้งาน, `version` กันบันทึกทับจากหน้าต่างที่เปิดค้าง (`ITEM_VERSION_CONFLICT`) และเก็บประวัติ snapshot ก่อน/หลังในธุรกรรมเดียวกับการบันทึก ส่วนที่ระบบนี้เพิ่ม: บันทึกผู้แก้ (persona) และ `audit_logs` ที่ระบุ admin ตัวจริง
- **เปิดเฉพาะโหมดทดสอบ**: ทุก RPC ปฏิเสธนอกโหมดทดสอบด้วย `FACTORY_TEST_MODE_ONLY` (`private.factory_actor`) ในโหมดทดสอบ persona ใดก็เพิ่ม/แก้ Item ได้ เพราะเข้าโหมดทดสอบได้เฉพาะ admin ข้อมูลแยกด้วย `is_test` ตามกติกา 5 ข้อด้านบน (trigger `factory_sandbox_scope`, foreign key คู่ `(id, is_test)` ทำให้แถวทดสอบอ้างแถวจริงไม่ได้, รหัสไม่ซ้ำแยกตามโหมด) **ก่อนเปิดกับข้อมูลจริงต้องกำหนดเจ้าของข้อมูลหลัก แหล่งข้อมูล และบทบาทผู้แก้ไข** แล้วแก้ `factory_actor` พร้อมเทสต์อนุญาต/ปฏิเสธของบทบาทนั้น
- **ข้อมูลตัวอย่าง**: ปุ่ม "เติมข้อมูลตัวอย่าง" ใส่ข้อมูลสมมติจากแอปที่ส่งมา (16 Item, 3 คลัง, 5 ศูนย์งาน, BOM/Routing 3 ชุด, ใบสั่งผลิต 2 ใบ, ยอดยกมา) เติมได้ครั้งเดียวจนกว่าจะล้าง ชื่อ ขนาด สูตร และเวลาผลิตไม่ใช่ข้อมูลจริง ปุ่ม "ล้างข้อมูลทดสอบฝ่ายโรงงาน" ลบเฉพาะแถว `is_test` (แยกจากปุ่มล้างข้อมูล NCR ในแถบสีเหลือง)
- **ยังไม่มี**: แก้ BOM ที่อนุมัติแล้วโดยตรง (ออก Revision ใหม่แทน), สร้าง/แก้ Routing, การรับ-จ่าย/ย้ายคลัง, อัตราแปลงหน่วย (มีตาราง ยังไม่ใช้) และหน้าแผนภาพโครงสร้างข้อมูลของแอปเดิม (สรุปไว้ในตารางด้านบนและหัวไฟล์ migration แทน) การค้นหา/แบ่งหน้าทำในหน้าเว็บกับข้อมูลชุดเดียว ถ้าข้อมูลจริงหลักหมื่นรายการต้องย้ายไปทำที่ฐานข้อมูล
- **สร้างโครงสร้างสินค้า (BOM) → ส่งให้ admin อนุมัติ** (`20261007010000_factory_bom_draft_approval.sql`, Pilot Web รุ่น `20261007a`):
  - ขั้นตอน: `draft` → ส่งขออนุมัติ → `pending_approval` → ผู้ดูแลระบบ **อนุมัติ** (`approved`) หรือ **ไม่อนุมัติ+เหตุผล** (กลับเป็น `draft` ผู้ส่งแก้แล้วส่งใหม่) · ถอนกลับมาแก้ได้ก่อนตัดสิน · แก้เนื้อหาได้เฉพาะ `draft` · Revision เป็น A, B, C… ระบบกำหนดให้ · Item หนึ่งมีฉบับที่เปิดอยู่ (ร่าง/รออนุมัติ) ได้ 1 ฉบับและฉบับที่อนุมัติ 1 ฉบับ เมื่ออนุมัติฉบับใหม่ ฉบับที่อนุมัติเดิมเป็น `obsolete` ในธุรกรรมเดียวกัน
  - กฎที่ฐานข้อมูลบังคับ: สินค้าหลักเป็น Item ที่ใช้งานอยู่ ประเภท WIP/FG ผลิตเองได้ · ส่วนประกอบเป็น Item ที่ใช้งานอยู่ ไม่ซ้ำ ไม่ใช่สินค้าหลักเอง · **ห้ามสูตรวนซ้ำ** (ตรวจตอนบันทึก ส่ง และอนุมัติ ด้วยล็อก advisory) · ปริมาณ/ผลผลิต > 0 ปัดเป็น 4 ทศนิยม เผื่อสูญเสีย 0 ≤ x < 100 ไม่เกิน 100 บรรทัด · ส่งขออนุมัติต้องมีอย่างน้อย 1 บรรทัด · **หน่วย**: ปริมาณแต่ละบรรทัดเป็นหน่วยนับฐานของส่วนประกอบ ผลผลิตเป็นหน่วยฐานของสินค้าหลัก (หน่วยฐานล็อกหลังสร้าง) จึงไม่มีการแปลงหน่วยในสูตร · ตอนอนุมัติตรวจซ้ำว่า Item ยังใช้งานอยู่และไม่เกิดวงจรหลังส่ง
  - สิทธิ์: สร้าง/แก้/ส่ง/ถอนกลับ ทำได้ทุก persona ในโหมดทดสอบ · **อนุมัติ/ไม่อนุมัติ เฉพาะผู้ดูแลระบบตัวจริงเบื้องหลัง persona** (บันทึก `decided_by` และ `audit_logs` เป็น admin ไม่ใช่ persona) อนุมัติใบที่ตนส่งเองไม่ได้ (`BOM_SELF_APPROVAL`) และการตัดสินผูกกับ `version` ที่เห็น ถ้าใบถูกถอน/แก้/ส่งใหม่ระหว่างนั้น = `BOM_VERSION_CONFLICT`

  - **การแจ้งเตือน**: โหมดทดสอบไม่ส่งอีเมล/LINE (กติกาข้อ 4) การ "ส่งให้ admin" จึงเห็นเป็นคิวที่ **โครงสร้างสินค้า-อนุมัติ** และแบนเนอร์ในหน้าโครงสร้างสินค้าเท่านั้น ก่อนเปิดใช้กับข้อมูลจริงต้องกำหนดผู้อนุมัติจริง (ตอนนี้ผูกกับ admin) และช่องทางแจ้งเตือน

  - **ขั้นสุดท้ายเสร็จ = รับผลผลิตเข้าคลังจริง**: ตามจำนวนผลิตจริงที่ผู้ทำขั้นสุดท้ายกรอก (ไม่กรอก = จำนวนของใบงาน) เข้าคลังที่เลือกตอนออกใบงาน (`production_output` พร้อมล็อต `LOT-<เลขที่ใบงาน>` ถ้า Item ติดตามล็อต) ตัวอย่าง: ยางเส้นยาวเข้าคลัง SR เมื่อ QC ตรวจขนาดเสร็จ สินค้าสำเร็จรูปเข้าคลัง FG เมื่อ WH รับเสร็จ

### การอ่านหน้าใบงานฝ่ายโรงงาน

หน้าใบงานแสดงสินค้า จำนวน คลัง ขั้นปัจจุบัน และวัตถุดิบที่จะตัดก่อนฟอร์มทำงาน ตารางขั้นตอนทั้งหมดและประวัติพับไว้ให้เปิดดูเพิ่มเติม หาก QC ไม่ผ่านล่าสุดจะแสดงคำเตือนและเปิดผลตรวจ QC ไว้ การยกเลิกอยู่ในส่วนที่ต้องเปิดก่อนและยังต้องระบุเหตุผล/ยืนยันตามเดิม

เมนูข้างใช้ชื่อ “เมนูโรงงาน” และแสดงเฉพาะโฟลเดอร์ที่มีรายการ โดยคง URL ของรายการเดิม ปุ่มฝ่ายโรงงานบนมือถือมีความสูงอย่างน้อย 44px และช่อง QC ที่ซ่อนตามผลตรวจไม่แสดงหรือรับโฟกัส การจัดหน้าจอนี้ไม่เปลี่ยนสิทธิ์ ลำดับขั้น หรือกฎการตัด/คืน/รับสต็อก

```text
   ├─ Auth                  session แบบ cookie-backed SSR
   ├─ Postgres + RLS        employee, workflow, audit, notification
   └─ Private Storage       request-attachments (signed URL 60 วินาที)
```

การดำเนิน workflow ที่ต้องแก้หลายตารางใช้ secret key เฉพาะใน Server Actions หลังตรวจผู้ใช้และสิทธิ์แล้วเท่านั้น ส่วนการอ่านข้อมูลและการเพิ่ม comment/attachment ใช้ session ของผู้ใช้ผ่าน RLS โดยตรง Secret key ไม่ถูกส่งไป browser

## แจ้งเตือนทางอีเมล

การแจ้งเตือนเมื่อคำร้องเดินไปแต่ละขั้นส่งทางอีเมลแล้ว ไม่ได้ push เข้า LINE อีกต่อไป ตัวส่งอยู่ที่
`src/lib/notify.ts` (`notifyEmployeeByEmail`) ซึ่งอ่านอีเมลจาก Employee Master และข้ามบัญชีที่ปิด
ใช้งานแล้ว สัญญาของฟังก์ชันเหมือนตัวเดิมทุกอย่าง คือไม่โยน error ออกไป และคืน `{ ok, configured }`
ให้ผู้เรียกตัดสินใจ — อีเมลส่งไม่ออกต้องไม่ทำให้คำร้องล้ม

ช่องทางส่งเลือกจาก environment variable ไม่ผูกกับผู้ให้บริการรายใดในโค้ด

| ตั้งค่า | ผล |
|---|---|
| `RESEND_API_KEY` + `NOTIFY_EMAIL_FROM` | ส่งผ่าน Resend API |
| `NOTIFY_EMAIL_WEBHOOK_URL` | POST `{ to, subject, text }` ไปปลายทางที่กำหนด ใช้ต่อกับ Apps Script ที่ส่งอีเมลอยู่แล้วได้โดยไม่ต้องสมัครผู้ให้บริการใหม่ |
| ไม่ตั้งอะไรเลย | ไม่ส่ง คืน `configured:false` เงียบๆ ระบบยังทำงานครบ เหมือนตอน LINE ไม่มี token |

หัวเรื่องอีเมลคือบรรทัดแรกของข้อความ ซึ่งเป็นบรรทัดสรุปเรื่องอยู่แล้วในทุกจุดที่เรียก โครงข้อความ
จึงเหมือนที่เคยส่งเข้า LINE ทุกประการ

โค้ดส่วน LINE Login และ Rich Menu ยังอยู่ครบและยังใช้ผูกบัญชีได้ตามเดิม เพียงแต่ไม่ได้ถูกใช้ส่ง
แจ้งเตือนแล้ว ถ้าตัดสินใจเลิกใช้ LINE ทั้งหมดค่อยถอดออกทีเดียวพร้อมตาราง `line_accounts`

### อีเมลแจ้งเตือนของ Pilot Web (แยกช่องทางจาก `notify.ts` ข้างบน)

Pilot Web (`app.js`) เรียก Postgres RPC ตรงๆ ไม่ผ่าน Server Action ของ Next.js จึงส่งอีเมลด้วย
`notify.ts` ไม่ได้ — ใช้ Edge Function `supabase/functions/notify-email` แทน

ฟังก์ชันนี้ทำงานเป็น **คิว** ไม่ใช่ "ส่งตามคำสั่งของหน้าจอ" แถวใน `public.notifications` ที่
`email_status = 'pending'` คือคิวงาน ใครเรียกฟังก์ชันเมื่อไรก็ได้ ฟังก์ชันจะไล่ส่งแถวที่ยังค้าง
แล้วบันทึกผลจริงลงแถวนั้น (`sent` / `skipped` / `failed` พร้อม `email_error`) ไม่คำนวณผู้รับซ้ำ
ฝั่งไคลเอนต์ เพราะ RPC (security definer) เลือกผู้รับที่ถูกต้องไว้ให้แล้วตอน insert

| เรียกด้วย | ผล |
|---|---|
| `POST { requestId }` | เร่งส่งเฉพาะแจ้งเตือนของคำร้องนั้น ใช้ทันทีหลัง action สำเร็จ |
| `POST {}` | ไล่ทั้งคิว ครอบคลุมแจ้งเตือนที่ไม่ผูกกับคำร้อง (คำร้องเปิดบัญชี/แก้ไข ID ซึ่ง `request_id` เป็น `NULL`) และแถวที่ตกค้างจากรอบก่อน |
| `POST { action: "status" }` | คืนว่าตั้งค่าช่องทางส่งไว้หรือยัง ใช้ช่องทางไหน และมีกี่แถวค้างคิว |

จุดที่เรียก: ทุก action ที่ RPC insert แจ้งเตือน (สร้างคำร้อง/ใบแจ้งซ่อม, อนุมัติ, อัปเดตสถานะ,
มอบหมายช่าง, เริ่มงาน, บันทึกผลซ่อม, ตรวจรับ, คำร้องบัญชี) บวกกับ **ไล่คิวหนึ่งครั้งตอนเปิดแอป**
เพื่อกู้แถวที่ตกค้าง และ `pilot-auth` เรียกให้เองด้วย service role ในเส้นทางคำร้องเปิดบัญชี/อนุมัติ
ซึ่งผู้ยื่นยังไม่มี session ของตัวเอง

เนื้อหาอีเมลถูกประกอบที่ Edge Function ทั้งหมด ไม่ต้องแก้ RPC เพิ่ม: หัวเรื่องมีอีโมจิและเลขที่
คำร้อง ตัวอีเมลเป็น HTML มีแถบสีตามประเภทเรื่อง ตารางรายละเอียด (เลขที่ ประเภท เรื่อง สถานะ
ความสำคัญ ผู้ขอ หน่วยงาน เครื่องจักร กำหนดเวลา) และปุ่มลิงก์ตรงไปยังหน้ารายการนั้น โดยใช้กติกา
เดียวกับ `notificationHref()` ใน `app.js` เพื่อให้กดจากอีเมลแล้วไปถึงหน้าเดียวกับที่กดจากในเว็บ

ปลายทางของลิงก์อ่านจาก `APP_BASE_URL` (ไม่ตั้งจะใช้ `https://mnpchatai.github.io/MNP_SYSTEM`)
ย้าย host เมื่อไรก็แก้ที่ secret ตัวนี้ตัวเดียว ไม่ต้อง deploy ใหม่

ประโยคนำขึ้นต้นด้วยชื่อโมดูลจาก `request_types.name_th` เช่น "ใบคำร้อง/แจ้งซ่อม MT รอคุณอนุมัติ"
ผู้รับจึงรู้ว่าเรื่องอะไรตั้งแต่บรรทัดแรกโดยไม่ต้องเปิดอ่าน แจ้งเตือนที่ไม่ผูกกับคำร้อง (เรื่องบัญชีผู้ใช้)
ใช้ประโยคกลางๆ แทน

อีโมจิและสีเลือกจากคำในหัวเรื่อง ไม่ได้เทียบแบบตรงตัว แจ้งเตือนชนิดใหม่ที่ RPC เพิ่มภายหลังจึงได้
อีโมจิที่เข้าเรื่องเองโดยไม่ต้องกลับมาแก้: 📋 รออนุมัติ · 🔄 เปลี่ยนสถานะ · 🔧 มอบหมายงาน ·
🔍 ตรวจรับ · ✅ อนุมัติ · ❌ ไม่ผ่าน · 🔑 บัญชี

ค่าสถานะที่ RPC เขียนไว้เป็น enum อังกฤษ (`approved`, `more_info`) ถูกแปลเป็นไทยตอนประกอบอีเมล
และทุกค่าที่ผู้ใช้พิมพ์เองถูก escape ก่อนวางลง HTML เสมอ

หน้าผู้ดูแลระบบมีแถบสถานะอยู่บนสุด บอกว่าอีเมลแจ้งเตือนส่งออกได้หรือยัง ใช้ช่องทางไหน และค้างคิว
กี่รายการ พร้อมปุ่มสั่งส่งคิวที่ค้างเดี๋ยวนี้ — ถ้ายังไม่ได้ตั้ง secret แถบนี้จะเป็นสีแดงบอกให้ไปตั้ง
แทนที่จะเงียบไปเฉยๆ อย่างเดิม

เมื่อส่งไม่สำเร็จ ฟังก์ชันจะลองใหม่ได้สูงสุด 3 ครั้ง (นับที่ `email_attempts`) ครบแล้วจึงปิดเป็น
`failed` และอีเมลที่ส่งไม่ได้จริงตั้งแต่ต้น เช่น โดเมนสมมติอย่าง `@pilot.mnp.local` หรือผู้รับที่
ปิดใช้งานแล้ว จะถูกบันทึกเป็น `skipped` พร้อมเหตุผล ไม่นับเป็นความล้มเหลว

ไล่หาสาเหตุเมื่อผู้ใช้แจ้งว่าอีเมลไม่เข้า ดูได้จากฐานข้อมูลโดยตรง:

```sql
select created_at, title, email_status, email_attempts, email_error
  from public.notifications
 where email_status <> 'sent'
 order by created_at desc;
```

เลือกช่องทางส่งจาก secret ที่ตั้งไว้ ไม่ผูกกับผู้ให้บริการรายใดในโค้ด (ลอง Resend ก่อนถ้ามี
`RESEND_API_KEY` ไม่มีค่อย fallback ไป Gmail SMTP ด้วย `nodemailer`):

| ตั้งค่า | ผล |
|---|---|
| `RESEND_API_KEY` (+ `NOTIFY_EMAIL_FROM` ถ้ามี) | ส่งผ่าน Resend API — ไม่ต้องพึ่ง admin อีเมลของบริษัทเลย ใช้เมื่อ admin ปิดการสร้าง Gmail App Password ไว้ |
| `GMAIL_SMTP_USER` + `GMAIL_SMTP_APP_PASSWORD` | ส่งผ่าน `smtp.gmail.com:465` — ต้องเปิด 2-Step Verification ของบัญชีนั้นก่อนถึงจะสร้าง App Password ได้ที่ myaccount.google.com/apppasswords (คนละอย่างกับรหัสผ่านล็อกอินปกติ) |
| ไม่ตั้งอะไรเลย | ไม่ส่ง คืน `{ ok:true, sent:0, note:"..." }` เงียบๆ ไม่ throw ให้ผู้ใช้เห็น |

```bash
# ทางเลือก A: Resend (แนะนำถ้า admin อีเมลบริษัทปิด App Password ไว้)
npx supabase secrets set RESEND_API_KEY=re_xxx
npx supabase secrets set NOTIFY_EMAIL_FROM=you@company.com   # ไม่ตั้งจะใช้ onboarding@resend.dev (sandbox) แทน

# ทางเลือก B: Gmail SMTP
npx supabase secrets set GMAIL_SMTP_USER=you@company.com
npx supabase secrets set GMAIL_SMTP_APP_PASSWORD=xxxxxxxxxxxxxxxx
npx supabase secrets set NOTIFY_EMAIL_FROM=you@company.com   # ไม่ตั้งจะใช้ GMAIL_SMTP_USER แทน

npx supabase functions deploy notify-email
```

### อีเมลยืนยันการอนุมัติสิทธิ์เข้าระบบ (ID + ลิงก์ตั้งรหัสผ่านใหม่)

เมื่อ Admin อนุมัติคำร้องเปิดบัญชี/แก้ไข ID ระบบส่งอีเมลยืนยันให้ผู้ได้รับอนุมัติ (ถ้ามีอีเมลจริง) โดยแนบ
**ID เข้าใช้งาน + ลิงก์ตั้งรหัสผ่านใหม่** — **ไม่ส่งรหัสผ่านทางอีเมล** (ผู้ใช้ที่จำรหัสผ่านที่ตั้งไว้ตอนขอเปิดบัญชีได้
เข้าสู่ระบบด้วยรหัสเดิมได้ทันที) และมีการส่งย้อนหลังให้ผู้ที่ได้รับอนุมัติไปก่อนหน้านี้ผ่าน migration
`20260930020000_account_approval_setup_link_email`

- `app_apply_account_request` ตั้งธง `notifications.email_setup_link = true` ที่แจ้งเตือนตอนอนุมัติ ส่วน
  `notify-email` เห็นธงนี้จึงสร้างโทเค็น (สุ่ม 256 บิต) ตอนส่งอีเมลเท่านั้น เก็บลง `password_setup_tokens` เป็น SHA-256
  ใช้ได้ครั้งเดียว หมดอายุใน 7 วัน ตารางนี้เปิด RLS ไม่มี policy และถอน grant ทั้งหมด เข้าถึงได้เฉพาะ service role
- ลิงก์ในอีเมลคือ `#/set-password?token=...` (โทเค็นอยู่ใน fragment จึงไม่เข้า log ของเซิร์ฟเวอร์) หน้านั้นเปิดได้โดยไม่ต้องล็อกอิน
  เรียก `pilot-auth` action `password_setup_info` / `password_setup_complete` ซึ่งเปลี่ยนรหัสผ่านผ่าน Auth Admin API แล้วบันทึกลงคลัง
  ID/รหัสผ่านตามเดิม (คลังต้องตรงกับรหัสจริงเสมอ) พร้อม audit log ที่ไม่มีรหัสผ่าน
- ลิงก์หมดอายุ/ถูกใช้แล้ว: ให้ Admin ตั้งรหัสผ่านให้ผู้ใช้ผ่านหน้า Admin ตามเดิม
- ส่งเฉพาะ Pilot Web (GitHub Pages) — แอป Next.js ไม่มีหน้า `set-password` เพราะอีเมลชี้ไป Pilot Web อยู่แล้ว
  (ความต่างที่ตั้งใจ)
- ผู้ที่อีเมลเป็นค่า placeholder (เช่น `*.pilot.mnp.local`) จะถูกข้ามเป็น `skipped` เหมือนแจ้งเตือนอื่น

  Edge Function เลย การหน่วง 90 วินาทีกันไม่ให้ชนกับการส่งทันทีหลังอนุมัติของ `pilot-auth` (ถ้าชนจะเกิดอีเมลซ้ำ
  และลิงก์ตั้งรหัสผ่านฉบับแรกใช้ไม่ได้)
- งาน `cron-run-history-cleanup` ลบประวัติ `cron.job_run_details` ที่เก่ากว่า 7 วัน วันละครั้ง (pg_cron ไม่ลบเอง)
- ยังไม่ได้ตั้งช่องทางส่ง (Resend/Gmail) = แถว pending ไม่ถูกปิด งานจะเรียกทุกนาทีต่อไปแต่ไม่ส่งอะไร
- หยุดงานได้ด้วย `select cron.unschedule('notification-email-drain');`

### อีเมลเตือนของมาส่งหรือยัง (pg_cron)

หมุด "สั่งซื้ออุปกรณ์เรียบร้อย" ในใบแจ้งซ่อม (ดูหัวข้อ [หมุดความคืบหน้า](#หมุดความคืบหน้า)) ให้เลือก
ได้ว่ารับของทันที หรือระบุวันที่คาดว่าจะมาส่ง — ถ้าเลือกอย่างหลัง ระบบต้องเตือนถามทุกวัน 16:00 น.
เวลาไทยของวันที่คาดว่าจะมาส่ง ซึ่งไม่มี client เปิดแอปอยู่แน่นอนตอนนั้น จึงต้องให้ `pg_cron` ยิงงาน
เอง (`app_send_progress_step_reminders`) แล้วเรียก Edge Function `notify-email` ต่อทันทีผ่าน `pg_net`
(`private.dispatch_pending_notification_emails`) ไม่ใช่แค่ enqueue รอคนมาเปิดแอป

ไมเกรชัน `20260922040000_purchase_progress_delivery_reminders.sql` สร้างฟังก์ชัน+ตั้งเวลาให้ครบแล้ว
แต่ยังต้องตั้งค่าเพิ่มนอกไมเกรชัน (ทำครั้งเดียวผ่าน Supabase SQL editor — **ห้าม commit ค่าจริงลง
repo**) ก่อนอีเมลจะออกได้จริง:

1. เปิด extension `pg_cron` และ `pg_net` ให้โปรเจกต์ ถ้ายังไม่เปิด (Dashboard → Database →
   Extensions — ไมเกรชันมี `create extension if not exists` ให้แล้ว แต่บาง plan ต้องกดเปิดจาก
   Dashboard ก่อนสิทธิ์รันไมเกรชันจะสร้างได้)
2. ใส่ secret สองตัวลง Vault (ใช้ service role key จริงจาก Project Settings → API — คนละตัวกับ
   `SUPABASE_PUBLISHABLE_KEY` ที่ฝังใน `app.js` เพราะตัวนั้น publishable key เท่านั้น ไม่มีสิทธิ์พอ):
   ```sql
   insert into vault.secrets (name, secret) values
     ('notify_email_function_url', 'https://iqlydmkylqyowmvpsete.supabase.co/functions/v1/notify-email'),
     ('notify_email_service_role_key', '<service role key จริง>');
   ```
3. ตรวจว่าตั้งเวลาไว้แล้ว: `select * from cron.job where jobname = 'purchase-progress-step-reminders';`

ไม่ตั้ง 2 secret ข้างบน = หมุดยังตั้งวันที่คาดว่าจะมาส่งและแจ้งเตือนในหน้าเว็บได้ปกติ (แถวใน
`notifications` ยังถูกสร้างตามเวลาที่ตั้งไว้) เพียงแต่จะไม่มีอีเมลออกอัตโนมัติจนกว่าจะมีคนเปิดแอปมา
ไล่คิวเอง หรือตั้ง secret ครบ (เหมือนพฤติกรรมยังไม่ตั้งช่องทางส่งอีเมลปกติ ไม่ throw ให้ระบบอื่นพัง)

## ตั้งค่า LINE OA

สร้าง LINE Login channel และ Messaging API channel ภายใต้ Provider เดียวกัน เพื่อให้ user ID สอดคล้องกัน จากนั้น:

1. ตั้ง callback URL ของ LINE Login เป็น `https://YOUR_DOMAIN/api/line/callback`
2. ตั้ง Messaging API webhook เป็น `https://YOUR_DOMAIN/api/line/webhook`
3. สร้าง Default Rich Menu สำหรับคนทั่วไป: `เว็บไซต์ | ติดต่อเรา`
4. สร้าง Employee Rich Menu: `เว็บไซต์ | ติดต่อเรา | ระบบพนักงาน`
5. ตั้ง Default Rich Menu ที่ OA และนำ ID ของ Employee Rich Menu ใส่ `LINE_EMPLOYEE_RICH_MENU_ID`
6. ใส่ channel IDs/secrets/access token ใน `.env.local`
7. ให้พนักงาน Login เว็บ → Profile → เชื่อมต่อ LINE และเพิ่ม OA เป็นเพื่อน

Per-user Rich Menu มีลำดับสูงกว่า Default Rich Menu ระบบจึงผูก Employee Rich Menu หลังยืนยันพนักงาน ส่วนคนทั่วไปยังเห็น Default Menu หากผู้ใช้ยังไม่ได้เพิ่ม OA เป็นเพื่อน LINE อาจตอบสำเร็จแต่ไม่แสดงเมนู ระบบจะแจ้งให้ลองอีกครั้งหลังเพิ่มเพื่อน

Webhook ตรวจ `x-line-signature` กับ raw body ด้วย HMAC-SHA256 ก่อน parse หรือบันทึก event ตามคำแนะนำของ LINE

ตัวแปรทั้งหมดอยู่ใน [.env.example](.env.example) และไม่มี credential จริงใน repository

## รูปแนบจากโทรศัพท์ทุกรุ่น

ฟอร์มแนบไฟล์รับรูปจากโทรศัพท์ได้ทุกรุ่นโดยผู้ใช้ไม่ต้องแปลงเอง ระบบเตรียมรูปในเบราว์เซอร์ทันทีที่เลือกไฟล์
(`modules/attachment-image.js` ใช้ร่วมกันทั้ง Pilot Web และ Next.js ผ่าน `src/components/attachment-input.tsx`):

| ไฟล์ที่ผู้ใช้เลือก | สิ่งที่ระบบทำ |
|---|---|
| JPEG / PNG / WebP ไม่เกิน 4 MB | ใช้ไฟล์เดิม ไม่บีบซ้ำ (ภาพหน้าจอไม่เบลอ) |
| รูปใหญ่เกิน 4 MB (กล้องความละเอียดสูง) | ย่อด้านยาวไม่เกิน 2560 px แปลงเป็น JPEG |
| HEIC / HEIF (iPhone), AVIF, GIF, BMP, TIFF | แปลงเป็น JPEG (GIF ใช้เฟรมแรก) |
| ไฟล์ที่เบราว์เซอร์ไม่ระบุชนิด หรือไม่มีนามสกุล (เช่นรูปที่เซฟจาก LINE) | ดูชนิดจากเนื้อไฟล์จริง (magic bytes) แล้วจัดการตามแถวบน |
| PDF / TXT / DOCX / XLSX | ผ่านไปตามเดิม ใช้การตรวจชนิดเดิมของแต่ละหน้า |

- **ความปลอดภัยไม่เปลี่ยน:** server action และ bucket `request-attachments` ยังจำกัดชนิด (JPEG/PNG/WebP/PDF/TXT/DOCX/XLSX)
  และขนาด 20 MB ต่อไฟล์ (เดิม 10 MB — ดู "แนบหลายไฟล์พร้อมกัน" ข้างล่าง) ตัวเตรียมรูปแค่แปลงไฟล์ให้ผ่านเกณฑ์ ไม่เปิดชนิดไฟล์เพิ่ม
- **ขีดย่อรูป 4 MB** (ไม่ใช่เพดานไฟล์ 20 MB) เพราะ Server Action ของ Next.js บน Vercel รับ body ได้ราว 4.5 MB
- **HEIC:** Safari/iOS ถอดรหัสเองได้ จึงไม่โหลดอะไรเพิ่ม เบราว์เซอร์อื่นโหลด `libheif-js` เฉพาะตอนเจอรูป HEIC
  Pilot Web ใช้ build JavaScript ล้วนที่ `vendor/libheif/` (ไม่ต้องผ่อน CSP) ส่วน Next.js ใช้ `libheif-js/wasm-bundle`
  (เร็วกว่า และ Next.js ไม่มี CSP ที่ห้าม WebAssembly) รายละเอียดสัญญาอนุญาต LGPL-3.0 ดู `vendor/libheif/README.md`
- ระหว่างแปลงช่องแนบไฟล์ขึ้น "กำลังเตรียมรูป" และกดส่งฟอร์มไม่ได้ (`setCustomValidity`) ถ้าแปลงไม่สำเร็จจะล้างช่องและแจ้งข้อความ
  ให้บันทึกเป็น JPG แล้วแนบใหม่ มีเวลาจำกัด 60 วินาทีกันหน้าจอค้าง
- ช่อง "แนบไฟล์ใบเสร็จรายการอะไหล่" ในฟอร์มจบงานของ Pilot Web (ไม่ได้อยู่ในฟอร์มที่ส่งผ่าน `submit`) ก็ถูกแปลงด้วย
  แต่กดปุ่ม "แนบไฟล์" ก่อนแปลงเสร็จจะอัปโหลดไฟล์เดิม ให้รอข้อความ "เตรียมรูปเป็น JPG แล้ว" ก่อน

### แนบหลายไฟล์พร้อมกัน

ช่องแนบไฟล์ทุกจุด (สร้างคำร้อง, แนบเพิ่มในหน้าคำร้อง, ใบแจ้งซ่อม MT, ใบเสร็จอะไหล่, หลักฐาน NCR) เลือกได้หลายไฟล์ในครั้งเดียว

| กติกา | ค่า | ตรวจที่ไหน |
|---|---|---|
| ขนาดรวมต่อการแนบหนึ่งครั้ง | **ไม่เกิน 20 MB** (ไฟล์เดียวใช้ได้เต็ม 20 MB) วัดจากไฟล์ที่เตรียมแล้ว (หลังบีบรูปเป็น JPEG) ซึ่งเป็นขนาดที่อัปโหลดจริง | เบราว์เซอร์ (`checkBatch` ใน `modules/attachment-image.js`) |
| จำนวนไฟล์ต่อการแนบหนึ่งครั้ง | ไม่เกิน 10 ไฟล์ (นับก่อนแปลง กันเลือกรูปเป็นร้อยจนเครื่องค้าง) | เบราว์เซอร์ |
| ขนาดต่อไฟล์ | **ไม่เกิน 20 MB** (เดิม 10 MB) | check constraint ของ `request_attachments` / `ncr_attachments`, bucket ทั้งสองใบ, `app_ncr_add_attachment`, server action — migration `20261003000000` |
| ชนิดไฟล์ | JPEG/PNG/WebP/PDF/TXT/DOCX/XLSX — ไม่เปลี่ยน | server action / bucket |

- ขีดรวม 20 MB และ 10 ไฟล์เป็นการตรวจฝั่งเบราว์เซอร์ (UX) ส่วนเพดานต่อไฟล์ 20 MB บังคับจริงที่ฐานข้อมูลและ bucket
  ตัวเลขฝั่งเบราว์เซอร์/server action อยู่ที่ `MAX_FILE_BYTES` / `MAX_BATCH_BYTES` / `MAX_BATCH_FILES` ใน `modules/attachment-image.js` ที่เดียว
  (ข้อความใต้ช่อง `HINT` และข้อความ error อ้างค่าเดียวกัน) **ถ้าเปลี่ยนเพดานต้องเขียน migration ใหม่ให้ตรงกันด้วย** — ตัวอย่างดู `20261003000000_raise_attachment_size_limit_to_20mb.sql`
  (เพราะเคยยกแค่ฝั่งเบราว์เซอร์แล้วฐานข้อมูลยังเป็น 10 MB อยู่)
- **ลำดับ deploy เมื่อยกเพดาน:** `npx supabase db push` ก่อน (หรือพร้อม) การ deploy Pilot Web ไม่งั้นไฟล์ 10–20 MB ผ่านการตรวจฝั่งเบราว์เซอร์แต่ถูก Storage ปฏิเสธ
  และตรวจ "Global file size limit" ของ Storage ในโปรเจกต์ Cloud (Dashboard → Storage → Settings) ให้ไม่ต่ำกว่า 20 MB เพราะ bucket ตั้งเกินค่ารวมไม่ได้
  (`supabase/config.toml` ตั้ง `20MiB` ให้เฉพาะ local/CI)
- **ข้อจำกัดของ Next.js บน Vercel:** body ของ Server Action ถูกจำกัดราว 4.5 MB ก่อนถึงแอป รูปถูกบีบให้ไม่เกิน 4 MB จึงผ่าน
  แต่ไฟล์ที่ไม่ใช่รูป (PDF/DOCX/XLSX) ที่ใหญ่กว่านั้นอัปโหลดผ่าน Next.js บน Vercel ไม่ได้ (Pilot Web อัปโหลดตรงเข้า Storage จึงไม่ติด)
  ถ้าต้องรองรับถึง 20 MB บน Next.js ต้องเปลี่ยนเป็น signed upload URL ตรงเข้า Storage
- ตัวเตรียมไฟล์ทำทีละไฟล์ (ไม่ถอดรหัสหลายรูปพร้อมกัน เพราะมือถือหน่วยความจำไม่พอ) แสดงความคืบหน้า "(2/5)" ถ้าไฟล์ใดแปลงไม่ได้จะล้างการเลือกทั้งชุดและแจ้งชื่อไฟล์นั้น
  ไม่ปล่อยให้ส่งไฟล์ไม่ครบโดยไม่รู้ตัว ช่องไฟล์เดียว (ไม่มี `multiple`) ทำงานเหมือนเดิมทุกอย่าง
- **Pilot Web** อัปโหลดทีละไฟล์จากเบราว์เซอร์ตรงไป Supabase Storage; **Next.js** เรียก `uploadAttachmentAction` ทีละไฟล์ (`src/lib/attachment-upload.ts`)
  แทนการส่งทุกไฟล์ไปกับฟอร์มครั้งเดียว เพราะ Server Action บน Vercel รับ body ได้ราว 4.5 MB (รูปแต่ละใบถูกบีบให้ไม่เกิน 4 MB อยู่แล้ว)
- การสร้างคำร้องแล้วแนบไฟล์ทำเป็นสองขั้น (สร้างคำร้อง → อัปโหลดไฟล์) ถ้าบางไฟล์แนบไม่สำเร็จ คำร้องยังอยู่และระบบแจ้งชื่อไฟล์ที่พลาดให้แนบใหม่ในหน้าคำร้อง
  (Next.js เดิมจะลบคำร้องทิ้งเมื่ออัปโหลดไฟล์พลาด ตอนนี้เปลี่ยนให้ตรงกับ Pilot Web)
- ทดสอบ: `npm run test:unit` ครอบคลุมตรรกะจำนวน/ขนาดรวม ส่วนการบีบรูปและช่องเลือกไฟล์ต้องทดสอบในเบราว์เซอร์

### ตัวอย่างไฟล์ก่อนอัปโหลด

เลือกไฟล์แล้ว (และเตรียมไฟล์เสร็จ) ระบบแสดง "ตัวอย่างไฟล์ที่จะส่ง" ใต้ช่องแนบไฟล์ทันที ก่อนกดอัปโหลด/ส่งฟอร์ม ใช้ทุกช่องที่แนบไฟล์ได้ (ทั้ง Pilot Web และ Next.js)
หน้าตาเป็นกระเบื้องชุดเดียวกับแกลเลอรีไฟล์แนบในหน้ารายละเอียด แต่เล็กกว่าและกดไม่ได้:

| ชนิดไฟล์ | ตัวอย่างที่แสดง |
|---|---|
| รูปภาพ | ภาพย่อ (ด้านยาว 360 px) พร้อมป้าย "รูปภาพ" |
| PDF | หน้าแรกของไฟล์ + ป้ายจำนวนหน้า เช่น "PDF · 2 หน้า" (pdf.js) |
| TXT | ข้อความต้นไฟล์ (600 ตัวอักษรแรก) |
| Word / Excel | ป้ายและไอคอนชนิดไฟล์ |
| ไฟล์ที่สร้างตัวอย่างไม่ได้ (PDF เสีย/ติดรหัสผ่าน) | ข้อความ "แสดงตัวอย่างไม่ได้" — ไฟล์ยังส่งได้ตามปกติ |

- ตัวอย่างสร้างจาก "ไฟล์ที่เตรียมแล้ว" ซึ่งเป็นไฟล์ที่จะถูกส่งจริง (รูป HEIC ที่แปลงเป็น JPG แล้วจะเห็นเป็น JPG) และอ่านจากไฟล์ในเครื่องโดยตรง ไม่เรียกเครือข่าย
  จึงไม่ต้องแก้ CSP ของ Pilot Web (`img-src` มี `data:` อยู่แล้ว; PDF ส่งให้ pdf.js เป็น data ไม่ใช่ blob URL เพราะ `connect-src` ไม่อนุญาต blob:)
- ทำทีละไฟล์ตามลำดับ: ภาพย่อผ่านคิวใน `createThumbnail` (`modules/attachment-image.js`) เพราะรูปจากมือถือถอดรหัสแล้วกินหน่วยความจำหลายสิบ MB ต่อใบ
  PDF ถูกอ่านเข้าหน่วยความจำเพื่อเรนเดอร์หน้าแรกแล้วคืนทันที ไม่แคช เลือกไฟล์ใหม่ระหว่างที่ยังสร้างไม่เสร็จ งานชุดเก่าถูกทิ้ง
  ล้างตัวอย่างเมื่อยกเลิกการเลือก/เลือกใหม่/เกินกติกา (ตัวอย่างจึงตรงกับชุดไฟล์ที่จะส่งเสมอ)
- **ปุ่ม × ลบทีละไฟล์:** มุมขวาบนของแต่ละกระเบื้อง ลบแล้วไฟล์นั้นหายจากชุดที่จะส่งจริง (เขียนชุดที่เหลือกลับลง `input.files` ผ่าน `removeSelectedFile`
  ใน `modules/attachment-image.js` ไม่ใช่แค่ซ่อนบนหน้าจอ) ข้อความสรุปปรับตามไฟล์ที่เหลือ กระเบื้องที่เหลือไม่ถูกวาดใหม่ (ไม่ถอดรหัสรูป/เรนเดอร์ PDF ซ้ำ —
  Next.js ใช้ id คงที่เป็น key) ลบจนหมดแล้วช่องว่างและ `required` กลับมาบังคับตามเดิม ปุ่มเป็น `type="button"` จึงไม่ส่งฟอร์ม ใช้คีย์บอร์ดได้ (โฟกัสกลับที่ช่องไฟล์)
  ระบุไฟล์ที่จะลบด้วยลำดับ ไม่ใช่ชื่อ จึงลบถูกใบแม้ชื่อและขนาดซ้ำกัน
- ชื่อไฟล์ใส่ด้วย `textContent` (Pilot) / React (Next.js) ไม่ผ่าน `innerHTML` เพราะชื่อไฟล์มาจากผู้ใช้
- **Pilot Web:** `modules/attachment-preview.js` (โหลดใน `index.html` ก่อน `app.js`) ถูกเรียกผ่าน `onSelection` ของ `bindFileInputs` ใน `app.js`
  **Next.js:** `src/components/attachment-selection-preview.tsx` ใช้ใน `AttachmentInput` — สองฝั่งเขียนแยกกันเพราะ DOM คนละแบบ ถ้าเปลี่ยนกติกาตัวอย่าง (ขนาดภาพย่อ ความยาวข้อความ) ต้องแก้ทั้งสองที่
- ทดสอบ: `npm run test:unit` ครอบคลุมฟังก์ชันล้วน (`scripts/tests/attachment-preview.test.mjs`) ส่วนการวาดภาพย่อ/pdf.js/DOM ต้องทดสอบในเบราว์เซอร์จริง

ข้อจำกัด: รูป TIFF บนเบราว์เซอร์ที่ไม่ใช่ Safari และไฟล์รูปที่เสีย แปลงไม่ได้ (ระบบแจ้งให้บันทึกเป็น JPG)
ถ้าปรับ `modules/attachment-image.js` ต้องเลื่อน `?v=` ใน `index.html` ตามกฎของ Pilot Web ด้วย

## Database และความปลอดภัย

- ทุกตารางใน exposed `public` schema เปิด RLS
- `anon` ไม่มีสิทธิ์อ่านข้อมูลภายใน
- พนักงานอ่านเฉพาะคำร้องที่ตนเป็นผู้ขอ ผู้รับผิดชอบ (รวมช่างทุกคนในชุดที่ถูกมอบหมาย ไม่ใช่เฉพาะคนแรก) หรือผู้อนุมัติ
- ผู้จัดการแผนกที่เป็น "เจ้าของประเภทเอกสาร" (`request_types.owning_department_id`) อ่านใบของประเภทนั้นได้ทุกใบ เพื่อให้ตรงกับอำนาจมอบหมายช่างที่ `app_assign_repair_technician` ให้ไว้ — เป็นสิทธิ์อ่านอย่างเดียว ไม่ได้แตะสิทธิ์อนุมัติ
- พนักงานทุกคนเห็น **สถานะ** ของทุกใบได้ผ่าน RPC `app_request_status_board` เท่านั้น ซึ่งคืนเฉพาะข้อมูลระดับติดตามสถานะ ไม่ใช่รายละเอียดคำร้อง
- Client ไม่มีสิทธิ์เขียน request/approval โดยตรง; ทุก transition ทำผ่าน Server Action ที่ตรวจผู้ใช้ บทบาท และสถานะก่อนใช้ server-only key
- Authorization ใช้ข้อมูล role/permission ในฐานข้อมูล ไม่ใช้ user-editable metadata ใน JWT
- Attachment bucket เป็น private และจำกัด 20 MB ต่อไฟล์ / MIME type
- LINE webhook ต้องผ่าน signature validation
- Audit trigger ครอบคลุม employee, request, approval และ LINE link

ก่อน production ควรเปิด MFA สำหรับ admin, กำหนด retention ของ audit/webhook events, ตั้ง alert/log drain และทดสอบ restore จาก backup

### CI บน GitHub Actions

`.github/workflows/ci.yml` รันทุก PR ที่เข้า `main` ทุก push เข้า `main` และสั่งรันเองได้จากแท็บ Actions มี 3 job:

| Job | ตรวจอะไร |
| --- | --- |
| `Typecheck, lint, build` | `npm run typecheck`, `npm run lint`, `npm run build` (build ไม่ต้องใช้ env จริง ไม่มี secret ใน CI) |
| `Database tests` | เปิด Supabase stack local **ภายใน runner** แล้วรัน `npm run db:test` ไม่แตะ Supabase Cloud |
| `PR guards` (เฉพาะ PR) | `scripts/ci/check-pr-guards.sh` ตรวจสิ่งที่ git merge ตรวจไม่ได้ ดูหัวข้อถัดไป |

`PR guards` มีไว้กันปัญหาตอนหลาย PR (หลาย AI/session) เปิดพร้อมกัน:

1. `?v=` ของ `app.js`, `styles.css` และ `modules/*.js` ใน `index.html` ต้องตรงกัน และทุกไฟล์ใน `modules/` ต้องถูกโหลดใน `index.html`
2. ถ้า PR แก้ `app.js`, `styles.css` หรือไฟล์ใน `modules/` เลข `?v=` ต้องต่างจาก `main` ณ ตอนนั้น ถ้า PR อื่น merge ก่อนแล้วเลขชนกัน ให้เลื่อนเลขใหม่ตอน update branch
3. ห้ามแก้ ลบ หรือเปลี่ยนชื่อ migration ที่อยู่บน `main` แล้ว
4. migration ใหม่ต้องมี timestamp ใหม่กว่า migration ล่าสุดบน `main` ถ้า PR อื่นที่มี migration ใหม่กว่า merge ไปก่อน ให้เปลี่ยนชื่อไฟล์ของ PR นี้ก่อน merge

รันในเครื่องได้ด้วย `scripts/ci/check-pr-guards.sh origin/main` (ให้ `git fetch origin main` ก่อน)

สิ่งที่ CI **ตรวจไม่ได้**: ถ้าสอง PR สร้าง migration ที่ `create or replace` ฟังก์ชันเดียวกัน ไฟล์ที่ apply ทีหลังจะเขียนทับฟังก์ชันทั้งก้อนโดยไม่มี conflict ผู้ที่ merge ทีหลังต้องเปิดดูว่าฟังก์ชันถูกแก้ใน `main` ไปแล้วหรือยัง และเขียน migration ใหม่จากเวอร์ชันล่าสุดเสมอ

### เปิด branch protection ให้ `main`

ทำครั้งเดียวโดยเจ้าของ repository **หลังจาก CI รันสำเร็จอย่างน้อย 1 รอบแล้ว** (ชื่อ check จะขึ้นให้เลือกเฉพาะ check ที่เคยรันแล้ว)

1. เปิด GitHub → repository `MNP_SYSTEM` → **Settings** → **Rules** → **Rulesets** → **New ruleset** → **New branch ruleset**
2. **Ruleset name**: `protect-main`, **Enforcement status**: `Active`
3. **Target branches** → **Add target** → **Include default branch** (`main`)
4. เปิดกฎต่อไปนี้:
   - **Restrict deletions**
   - **Block force pushes**
   - **Require a pull request before merging** โดยตั้ง **Required approvals** เป็น `0` ถ้ามีคนดูแลคนเดียว (บังคับว่าต้องผ่าน PR แต่ไม่ต้องรอคนอื่น approve) หรือ `1` ถ้ามีผู้ review
   - **Require status checks to pass** → ติ๊ก **Require branches to be up to date before merging** → **Add checks** แล้วเลือก `Typecheck, lint, build`, `Database tests` และ `PR guards`
5. **Bypass list**: เว้นว่างไว้ ถ้าใส่ตัวเองไว้ จะ push เข้า `main` ตรงได้ในกรณีฉุกเฉิน แต่ AI session ที่ใช้สิทธิ์บัญชีเดียวกันก็จะ bypass ได้ด้วย
6. กด **Create**

หลังเปิดแล้ว:

- push เข้า `main` ตรง ๆ จะถูกปฏิเสธ ทุก AI/session ต้องทำงานบน branch ของตัวเองแล้วเปิด PR
- เมื่อ PR หนึ่ง merge แล้ว PR อื่นที่เปิดค้างจะขึ้นว่า out of date ต้องกด **Update branch** (หรือ merge `main` เข้า branch) และรอ CI ผ่านอีกรอบก่อน merge ได้ ข้อนี้ทำให้ผลรวมของสอง PR ถูกทดสอบก่อนเข้า `main` เสมอ
- GitHub Pages ยัง deploy จาก `main` เหมือนเดิม

## ลำดับสถานะ

คำร้องทั่วไป

```text
pending_approval
├─ more_info → รอผู้ขอให้ข้อมูล/ดำเนินการต่อในรอบถัดไป
├─ rejected
└─ approved → in_progress → completed
```

ใบแจ้งซ่อม (ประเภทที่ `uses_repair_workflow = true`) — ขั้นอนุมัติสุดท้ายไป `pending_assign`
ไม่ใช่ `approved` รายละเอียดทั้งเส้นอยู่ที่หัวข้อ "เส้นทางใบแจ้งซ่อม"

```text
pending_approval (ขั้น 1 ผจก.โรงงาน → ขั้น 2 ผจก.ทั่วไป)
├─ more_info → ผู้แจ้งตอบกลับ → กลับมาขั้นเดิม
├─ rejected
└─ pending_assign → assigned → in_progress → pending_verify
                       ↑                          │
                       └── ตรวจรับไม่ผ่าน ─────────┤
                                                  └── ผ่าน → completed
```

Phase ถัดไปสามารถต่อยอดจาก request ที่อนุมัติแล้วเป็น Work Order, Asset/Machine Master, PM Plan, downtime, spare parts และต้นทุนซ่อมได้โดยไม่ต้องเปลี่ยนแกน identity/workflow นี้

### งานหลัก

1. **Identity และ Account Lifecycle**
   - ปิด public sign-up และให้สร้างบัญชีผ่าน Admin/Provisioning flow เท่านั้น
   - กำหนดขั้นตอนพนักงานเข้าใหม่ ย้ายแผนก เปลี่ยนบทบาท ระงับ และลาออก
   - บังคับ unique mapping ระหว่าง `auth_user_id`, `employee_no` และ LINE user ID
   - เพิ่ม password policy, leaked-password protection และ MFA สำหรับ Admin
2. **Workflow Configuration**
   - แยก approval rule ออกจากโค้ดเป็น configuration ที่มี version และ effective date
   - รองรับ approver แบบ Manager, Role + Department, Named User และวงเงินอนุมัติ
   - คำร้องที่สร้างแล้วต้องอ้างอิง workflow version เดิม แม้มีการแก้กฎในภายหลัง
3. **Reliability และ Security**
   - เพิ่ม idempotency key ให้ create/approve/status transition เพื่อป้องกันการกดซ้ำ
   - ทุก transition ตรวจ current status และสิทธิ์ใน transaction เดียวกัน
   - เพิ่ม automated test สำหรับ RLS, RPC allow/deny และ workflow transition ที่ผิดลำดับ
   - ตั้ง backup/restore drill, error monitoring, structured log และ alert สำหรับ Edge Function
4. **Pilot Operations**
   - แยก Demo/Test data ออกจากข้อมูลใช้งานจริง
   - จัดทำ UAT script ตามบทบาท Employee, Approver, Operator และ Admin
   - เพิ่ม in-app feedback และช่องทางรายงาน incident โดยอ้างอิง request number
   - เก็บตัวชี้วัด: login success, request completion rate, approval lead time, error rate และจำนวนงานค้าง

### Logic กลางของทุกคำสั่ง

```text
User action
   ↓
ตรวจ session และ employee = active
   ↓
ตรวจ permission + data scope
   ↓
ตรวจ current state + transition ที่อนุญาต
   ↓
ทำ domain transaction
   ├─ บันทึกข้อมูลหลัก
   ├─ บันทึก status history
   ├─ บันทึก audit event
   └─ สร้าง notification/outbox event
   ↓
Commit สำเร็จเพียงครั้งเดียว
   ↓
Worker/Edge Function ส่ง LINE หรือ notification แบบ retry ได้
```

Notification ต้องแยกออกจาก transaction หลักด้วย outbox pattern เพื่อให้คำร้องไม่ล้มเพียงเพราะ LINE API ช้า และต้องมี event key ป้องกันการแจ้งเตือนซ้ำ

### LINE Account และ Rich Menu Workflow

```text
ผู้ใช้ทั่วไปเพิ่ม LINE OA
   ↓
เห็น Default Rich Menu: เว็บไซต์ | ติดต่อเรา

พนักงาน Login Web App
   ↓
ตรวจ employee active + ขอ consent เชื่อม LINE
   ↓
LINE OAuth callback ตรวจ state/nonce
   ↓
ผูก employee ↔ LINE userId แบบ unique
   ↓
Link Per-user Employee Rich Menu
   ↓
ส่งแจ้งเตือนเฉพาะเหตุการณ์ที่ผู้ใช้มีสิทธิ์เห็น

พนักงาน inactive / ลาออก / ยกเลิกการเชื่อม
   ↓
Unlink Per-user Rich Menu + revoke link
   ↓
กลับไปใช้ Default Rich Menu
```

ห้ามถือว่า Web Login เพียงอย่างเดียวสามารถระบุ LINE account ได้ การผูก LINE ต้องเกิดผ่าน OAuth/consent และต้องยกเลิกได้จากทั้งผู้ใช้และ Admin

### เกณฑ์ผ่าน Phase 1.1

- UAT หลักผ่านครบ: สร้างคำร้อง → อนุมัติ → รับงาน → เสร็จสิ้น และ Reject/More Info
- ผู้ใช้ที่ไม่มีสิทธิ์ไม่สามารถอ่านหรือเปลี่ยนคำร้องผ่าน UI, REST หรือ RPC
- ไม่มี P0/P1 defect ที่ยังเปิดอยู่ และ failed transaction ไม่ทิ้งข้อมูลครึ่งชุด
- LINE failure ไม่ทำให้ business transaction ล้ม และระบบ retry โดยไม่ส่งซ้ำ
- ทดสอบ restore backup ได้จริง และมี runbook เมื่อ login/database/LINE ขัดข้อง
- Pilot users ยอมรับ workflow และมี owner รับผิดชอบ master data แต่ละชุด

## Phase 2 — Maintenance System

Phase 2 เป็นลำดับถัดไปที่เหมาะสมที่สุด เพราะ Phase 1 มีใบแจ้งซ่อม ผู้อนุมัติ และ Operator แล้ว จึงต่อยอดเป็น Work Order ได้โดยไม่ต้องเปลี่ยนแกนระบบ

### ขอบเขตข้อมูล

- Machine/Asset Master, location, criticality และสถานะทรัพย์สิน
- Work Order, assignment, SLA, priority และช่างผู้รับผิดชอบ
- Labor log, downtime, repair cause, corrective action และค่าใช้จ่าย
- Spare parts usage โดย Phase นี้บันทึกการใช้ก่อน ยังไม่ตัด Stock จนกว่า Phase 5 พร้อม (การบันทึกรายการอะไหล่ต่อใบทำได้แล้วผ่าน `requests.parts_used_items` เหลือส่วนเชื่อมกับ Material Master และต้นทุน)
- PM Plan, schedule, checklist และประวัติการซ่อมย้อนหลัง
- Requester confirmation, reopen reason และ closure feedback

### Maintenance Workflow

> **หมายเหตุ**: หัวข้อนี้เป็นภาพปลายทางของ Phase 2 ไม่ใช่สิ่งที่ระบบทำอยู่ตอนนี้ — workflow แจ้งซ่อม
> ที่ใช้งานจริงแล้ววันนี้อยู่ที่หัวข้อ **"เส้นทางใบแจ้งซ่อม"** ด้านบน ซึ่งเดินครบตั้งแต่เปิดใบจนตรวจรับ
> โดยยังไม่มีชั้น Work Order/SLA แยกออกมา

สิ่งที่ Phase 2 จะเพิ่มจากของที่มีอยู่แล้ว คือชั้น Work Order + SLA, สถานะพักงาน (`waiting_parts`,
`on_hold`) และการเก็บ labor/downtime/cost — ส่วนลำดับอนุมัติยังเป็น ผจก.โรงงาน → ผจก.ทั่วไป
ตามขั้นตอนจริง ไม่ใช่ "หัวหน้าแผนก → หน่วยงานซ่อมบำรุงคัดกรอง" อย่างที่เคยร่างไว้ในเอกสารรุ่นแรก

```text
แจ้งซ่อม (Request)
   ↓
ผู้จัดการโรงงานอนุมัติ → ผู้จัดการทั่วไปอนุมัติ      ← ทำได้แล้ววันนี้
   ↓
สร้าง Work Order + กำหนด SLA                      ← ของใหม่ใน Phase 2
   ↓
ผจก.ซ่อมบำรุงมอบหมายช่าง → ช่างเริ่มงาน            ← ทำได้แล้ววันนี้
   ↓
in_progress
   ├─ waiting_parts                               ← ของใหม่ (วันนี้ใช้หมุดความคืบหน้าแทน)
   ├─ on_hold (ต้องระบุเหตุผล/เวลานัดใหม่)          ← ของใหม่
   └─ repair_completed                            ← วันนี้คือ pending_verify
          ↓
ผู้แจ้งตรวจรับ
   ├─ ยืนยัน → closed                              ← วันนี้คือ completed
   └─ ไม่ผ่าน → reopened → in_progress             ← วันนี้ย้อนไป assigned
```

### Transition Rules

ตารางนี้เป็นกติกาเป้าหมายของ Phase 2 คอลัมน์ขวาสุดบอกว่าวันนี้ทำถึงไหนแล้ว

| จาก | ไป | ผู้ดำเนินการ | เงื่อนไขสำคัญ | สถานะวันนี้ |
|---|---|---|---|---|
| `approved` | `assigned` | ผจก.แผนกซ่อมบำรุง | มี assignee และข้อมูลการซ่อมบำรุงครบ | ✅ ทำแล้ว (`pending_assign` → `assigned`) |
| `assigned` | `in_progress` | ช่างที่ได้รับมอบหมาย | บันทึกเวลาเริ่ม | ✅ ทำแล้ว |
| `in_progress` | `waiting_parts` | ช่าง/Supervisor | ระบุอะไหล่และเหตุผล | ⏳ ยังไม่มีสถานะแยก — ใช้หมุดความคืบหน้าแทน |
| `in_progress` | `on_hold` | ช่าง/Supervisor | ระบุเหตุผลและ next action date | ⏳ ยังไม่มี |
| `in_progress` | `repair_completed` | ช่าง | ระบุสาเหตุและอะไหล่ที่ใช้ | ✅ ทำแล้ว (`pending_verify`) |
| `repair_completed` | `closed` | ผู้แจ้ง | ผ่านการตรวจรับ | ✅ ทำแล้ว (`completed`) |
| `repair_completed` | `reopened` | ผู้แจ้ง | ระบุเหตุผลที่ไม่ผ่าน | ✅ ทำแล้ว (ย้อนไป `assigned`) |
| `reopened` | `in_progress` | ช่างที่ได้รับมอบหมาย | เปิด labor/downtime รอบใหม่ | ✅ ทำแล้ว (ยังไม่เก็บ labor/downtime) |

ห้ามข้ามสถานะด้วยการ update ตารางโดยตรง ทุก transition ต้องผ่าน domain service/RPC และสร้าง status history เสมอ

### Dashboard และ KPI

- Open, Assigned, In Progress, Waiting Parts, Overdue และ Reopened jobs
- Mean Time to Acknowledge (MTTA), Mean Time to Repair (MTTR) และ downtime
- Planned vs Unplanned Maintenance
- PM compliance และงาน PM เกินกำหนด
- Repeat failure แยกตาม asset/cause
- ค่าแรง อะไหล่ และค่าใช้จ่ายต่อเครื่องจักร

### เกณฑ์ผ่าน Phase 2

- Work Order เชื่อมกลับไปยัง request และ asset ได้ทุกใบ
- SLA/overdue คำนวณจากเวลาที่บันทึกจริงและรองรับ on-hold policy
- ช่างเห็นเฉพาะงานในขอบเขตที่รับผิดชอบ และ Supervisor มองเห็นภาพรวมของหน่วยงาน
- ประวัติ asset แสดง request, work order, downtime, parts และ cost ครบ
- PM schedule สร้างงานได้แบบ idempotent และไม่สร้างซ้ำเมื่อ worker retry
- Dashboard KPI ตรงกับข้อมูลดิบที่ตรวจสอบย้อนหลังได้

## Phase 3–8 — Workflow ระดับโมดูล

### Phase 3 — HR Request

```text
Employee → Supervisor → HR Review → Management (ตามประเภท) → HR Complete
```

เริ่มจากลางาน อบรมภายนอก ขอว่าจ้าง เปลี่ยนตำแหน่ง ลาออก และการประเมิน โดยยังไม่รวม Payroll ข้อมูล HR ต้องมี permission แยกจากคำร้องทั่วไปและกำหนด retention/audit ที่เข้มกว่า

### Phase 4 — Procurement

```text
PR → Budget/Approval Limit → Procurement Review → RFQ
   → Price Comparison → Approval → PO Reference → Receiving Status → Complete
```

หาก PO อยู่ใน I-Prime ให้เก็บ reference และ sync status แทนการสร้าง PO ซ้ำ โดย integration ต้องมี external ID, last sync time และ reconciliation report

### Phase 5 — Stock / Material

```text
Material Request → Approve → Reserve → Issue
   ├─ Return
   ├─ Transfer
   └─ Adjustment (ต้องอนุมัติ)
```

ทุก movement ต้องเป็น immutable ledger การแก้ยอดทำผ่าน reversal/adjustment ไม่แก้ transaction เดิม และคำนวณ balance จาก movement ที่ตรวจสอบย้อนกลับได้

### Phase 6 — Production Tracking

```text
Customer Order → Production Order → Routing
   → RB/GR/PT/BG/PK → Partial Completion → Finished
```

เก็บ plan/actual/reject quantity, start/finish, WIP และ delay reason รองรับ partial completion โดยห้ามให้ actual good + reject เกินปริมาณที่รายงานเข้าขั้นตอน

### Phase 7 — QA / NCR / CAR

```text
Incoming/In-process/Finished Inspection
   ├─ Pass → ขั้นตอนถัดไป
   └─ Fail → NCR → Containment → Root Cause → CAR
                → Effectiveness Check → Close
```

ผลตรวจต้องอ้างอิง lot/order/asset ที่ตรวจ NCR และ CAR ต้องมี owner, due date, evidence และการตรวจประสิทธิผลก่อนปิด

### Phase 8 — Document Control

```text
Draft → Review → Approve → Effective
   ↓ revision ใหม่
Superseded/Obsolete → เก็บเพื่อ Audit แต่ผู้ใช้ทั่วไปเปิดไม่ได้
```

ควบคุม Document Code, revision, owner, effective date, distribution และ retention พนักงานเห็นเฉพาะ revision ที่ effective ตามหน่วยงาน/สิทธิ์ ส่วน Document Controller และ Auditor ดูประวัติได้

## กติกาการเริ่ม Phase ใหม่

ก่อนเริ่ม Phase ถัดไปต้องผ่าน Quality Gate ต่อไปนี้:

1. Scope และ process owner ลงนามรับรอง workflow/to-be process
2. Master data owner และแหล่งข้อมูลหลักถูกระบุชัดเจน
3. Permission matrix และกรณี segregation of duties ผ่านการทบทวน
4. Migration, rollback, backup และ reconciliation plan พร้อม
5. Automated test ครอบคลุม happy path, deny path, retry และ concurrent update
6. UAT ผ่านด้วยบัญชีจริงอย่างน้อยหนึ่งคนต่อบทบาท
7. Dashboard/KPI มีนิยามเดียวกับฝ่ายงานและตรวจย้อนกลับถึง transaction ได้
8. มี runbook, owner หลัง go-live และแผนเก็บ feedback รอบถัดไป

Roadmap นี้เป็นลำดับเชิง dependency ไม่ใช่ข้อบังคับว่าต้องเปิดทุกโมดูล หาก Phase ใดไม่มี process owner หรือ master data พร้อม ให้ชะลอ Phase นั้นและเลือกงานย่อยที่ใช้แกนเดิมได้โดยไม่สร้างข้อมูลซ้ำหรือ workflow คู่ขนาน
