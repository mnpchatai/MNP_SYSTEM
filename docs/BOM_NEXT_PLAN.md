## วิธีทำงาน (ใช้กับทุกชุด)

- หนึ่งชุด = หนึ่ง PR = หนึ่ง session ย่อย ทำทีละชุดตามลำดับ เพราะทุกชุดแตะ `index.html` (`?v=`) และไฟล์ `modules/bom-*.js` ชุดเดียวกัน ห้ามทำขนาน
- session ที่สั่งงาน (Opus) เป็นคนวางงาน อ่านผล และคุยกับผู้ใช้ งานลงมือให้ agent ทำตามตารางของแต่ละชุด
- ผู้ใช้ลองรอบเดียวต่อชุด: ลิงก์ localhost จาก Pilot harness ที่ใส่ข้อมูลสาธิตเอง พร้อมหน้าสรุป "ปรับปรุงอะไรบ้าง" แยกตามหน้าจอ
- push / เปิด PR / merge หลังผู้ใช้สั่งใน session นั้นเท่านั้น migration ต้องขออนุมัติก่อนใช้กับฐานข้อมูลจริงทุกครั้ง แล้วทำตาม "Deployment order" ใน `AGENTS.md` (เทียบ md5 ของฟังก์ชันก่อนและหลัง)
- ตรวจกติกากับ `supabase/migrations/` และ `scripts/pilot-harness-mock.mjs` ทุกครั้ง ไม่เชื่อ mock อย่างเดียว

### agent ที่ใช้และรุ่นโมเดล

| ขั้น | agent | โมเดล | หมายเหตุ |
|---|---|---|---|

| ตรวจก่อน merge | `auditor` | ค่าเริ่มต้น · `model: "opus"` เมื่อชุดนั้นมี migration หรือแตะ RPC/สิทธิ์ | commit ก่อนเรียก ให้โจทย์กับ diff ไม่ให้ข้อสรุป หนึ่งรอบต่อ PR รันซ้ำเฉพาะเมื่อแก้ข้อ blocking ที่เปลี่ยนโค้ด |

## ชุด A · อุดช่องที่ทำให้ใบค้างปิดไม่ได้ (มี migration เล็ก)

เป้าหมาย: ใบสั่งผลิตต้องปิดได้เสมอ และ mock ตอบเหมือนฐานข้อมูลจริง

1. ห้ามลด `qty_done` ของงาน PK/FG ต่ำกว่ายอดที่ WH รับสะสมแล้ว ใน `private.bom_save_jobs` (นิยามล่าสุดอยู่ที่ `20261111010000_bom_part_stock.sql` ให้เริ่มจากนิยามล่าสุดบน `main`) พร้อม pgTAP allow/deny · ตอนนี้ถ้ามีคนลดยอดผ่าน RPC ตรง `closeOrderShort` จะไม่ผ่าน (`v_received <> pk_done` ใน `private.bom_fg_move`) และใบค้าง
2. ST แก้ `safetyKg` ของเคมีด้วย `createPurchaseOrder` ที่มีแต่ชุด `materials`: อยู่ในกติกา "ST ตั้งสต็อกขั้นต่ำได้" แต่ยังไม่มี pgTAP ทั้ง allow และ deny (`rf_purchase_orders.test.sql`)
3. client รุ่นเก่าที่ไม่ส่ง `storedSafetyKg` เขียนค่าเก่าทับได้: ใน `private.rf_save_purchase_orders` ให้ ST ที่ไม่ใช่ฝ่ายวางแผนเปลี่ยนได้เมื่อส่ง `storedSafetyKg` เท่านั้น และทำ mock ให้ตรง
4. mock ไม่ตรง SQL 4 จุด (`scripts/pilot-harness-mock.mjs` เทียบ `20261121010000_bom_fg_receive_deliver.sql`):

   - คำสั่ง `receiveFg` / `deliverFg` / `closeOrderShort` ที่ไม่มี `fgMoves` หรือ `upsert` ว่าง: mock ตอบ `BOM_INVALID_FG` · SQL คืนสำเร็จแบบไม่ทำอะไร → **ให้ SQL เข้มขึ้นเป็น `BOM_INVALID_FG`** ตามสัญญา "exactly one request" (รวมใน migration ของชุดนี้) แล้วแก้ pgTAP ที่คาดหวังแบบเดิม
   - audit: mock นับจำนวนคำขอและไม่มี `orders +1` ตอนปิดใบ · SQL นับแถวประวัติและ `orders` 1 เมื่อปิด
   - `completeOrder` จากกลุ่มวางแผน: mock ตอบ `BOM_FORBIDDEN` · ฐานข้อมูลจริงตอบ `BOM_INVALID_ACTION` → ให้ mock มีรายการคำสั่งที่อนุญาตแบบเดียวกับ `private.bom_client_actions()` และแก้ `scripts/tests/bom-remote.test.mjs` ที่ยืนยันค่าของ mock
5. `fgRead` ใน `modules/bom-actions.js` ตรวจ `qty > 0` หลังปัด · เทสต์ `orderId` ตัวเล็กหรือมีช่องว่าง (SQL ทำ upper + trim)

## ชุด C · สต็อกสินค้าสำเร็จรูปลดงานผลิตของใบร่าง (รอผู้ใช้ตัดสินกติกา)

ตอนนี้ยอดคงคลังสินค้าสำเร็จรูป (รับ − ส่ง) แสดงอย่างเดียว และ `releaseOrder` ระบุว่าของในคลังไม่ลดงานบรรจุ

**ต้องถามผู้ใช้ก่อนเริ่ม หนึ่งคำถาม:** ของที่รับเข้าคลังแล้วแต่รอส่งลูกค้าของใบหนึ่ง ใบอื่นหยิบไปใช้ได้หรือไม่ หรือใช้ได้เฉพาะส่วนที่ผลิตเกินจำนวนสั่ง

หลังได้คำตอบ: `researcher` สำรวจ `rules.netRequirements`, `releaseOrder`, `private.bom_fg_move` และผลต่องาน PK → session หลักเขียนกติกาเป็นข้อๆ ให้ผู้ใช้ยืนยัน → `coder` (`opus` ถ้าต้องมี migration) → `auditor` (`opus`) · เคมียังไม่ถูกจองระหว่างใบร่าง ให้ถามผู้ใช้ในรอบเดียวกันว่าต้องการหรือไม่
