### 1.2 โครงสร้างข้อมูล BOM ที่ซ่อนอยู่ในชีต

- **สินค้าสำเร็จรูป (FG)** รหัส = `<ฐาน>(<แพ็กเกจ>)-<ชุดสี>` เช่น `MEGA-ST-01(P)-Y` ฐาน `MEGA-ST-01`
- **บรรทัดส่วนประกอบ** มี `รหัสแผนกที่ผลิต` 5 ค่า: `ST` (ซื้อ/คลัง 15,422 บรรทัด) · `SE` (ชิ้นยางย่อย 6,514) · `RB` (เส้นยาง 6,927) · `PK` (ตัวสินค้า 1,384) · `BG` (3)
  และ `แผนกผู้ผลิต` เป็น **คู่ ผู้ใช้-ผู้ผลิต** เช่น `PK-ST` (PK ใช้ของจากคลัง) `PT-ST` (PT ใช้เม็ดพลาสติก) `BG-ST` (BG ใช้ผ้า/ซิป) `PK-PT` `PK-BG` `BG-PT` `GR-ST` `PK-PK`
- **BOM เป็นหลายชั้นแต่ถูกเก็บแบบแบน**: FG → SE → RB (บรรทัด RB ตามหลัง SE และคอลัมน์ `ชิ้นงานถัดไปของ RB นี้` ชี้กลับไปที่ SE) · FG → PT → เม็ดพลาสติก (ST) · FG → BG → ผ้า/ซิป (ST) · FG → บรรจุภัณฑ์ (ST) ต้นไม้เดียวกันจึงถูกคัดลอกซ้ำในทุก FG ที่ใช้
- **รหัสชิ้นงานยางเข้ารหัสคุณสมบัติในตัว**
  `RB-<สูตรยาง>-<ประเภท 01 ตัน/02 มีรู/03 แผ่น>-<สี RB>-<ความยาว>-<รู/ความหนา>-<วงนอก>` เช่น `RB-B0006-02- -202-18-70`
  `SE-<สินค้า>-<สี>-<ความยาว>-<รู/หนา>-<วงนอก>` เช่น `SE-ST01--100-18-65`
  สี = แม่สี + เฉด สูงสุด 3 สี (`OR`+`01` → `OR01`) · `สูตรยาง` คือรหัสคอมปาวด์ (พบ 40 รหัส: `A1802 A2003 … B0006 … C1302`) ซึ่งตรงกับ "สูตรยาง (PHR)" ของ RubberFlow
- **สูตรปริมาณ** (จาก BOMSHEET): RB ต่อ SE = `1 / (จำนวน GR ตัดได้ต่อเส้น × จำนวน SE ต่อ 1 GR)` (ถ้าหน่วย RB เป็นกิโลกรัมใช้ `น้ำหนัก/1000`) · ต้องเบิก = จำนวน FG × จำนวนใช้ต่อ FG · ต้องผลิต/สั่งซื้อ = ต้องเบิก − คงคลัง (RB หักเศษตัดด้วย) · น้ำหนักต่อชิ้น/ต่อเส้น และตัวอย่างชั่ง 10 ครั้ง อยู่ใน master (6,342 บรรทัดมีค่าชั่ง)
- **ธงกระบวนการ** ใน master มี 9 คอลัมน์ แต่ใช้จริง 2: `เจาะ` (6,746) และ `คัดแยก` (7,151)

### 1.3 ข้อจำกัดที่ระบบใหม่ต้องแก้

1. **ไม่มี master เดียว**: `DATA` ถูกคัดลอกไปอยู่ในทุกไฟล์ PI (20 MB ต่อไฟล์) แก้ master แล้วใบเก่าไม่รู้ และสองชุด (ของเล่น/อุตสาหกรรม) แยกกัน
2. **คุณภาพรหัส**: 1,046 บรรทัดไม่มีรหัส (`-`/`0`) เป็นชิ้นที่ PK ทำเองหรือของ "ตามความเหมาะสม" · รหัส RB/SE 151 ตัวสะกดต่างกัน (ช่องว่าง/ขีดซ้ำ เช่น `RB-B0005-02--132-9-25` กับ `RB-B0005-02- -132-9-25`) · หน่วยนับ 356 แบบสะกด (`ชิ้น/pcs` `ชิ้น/pcs.` `กก.` `กิโลกรัม` `ม้วน(50M)` `ม้วน (50M)`) · หน่วยปนน้ำหนัก/จำนวนต่อแพ็ก (`กก.(112pcs)` `ชิ้น(20g)`)
3. **สถานะและการอนุมัติไม่มีในข้อมูล**: สถานะใบ = โฟลเดอร์, การแก้ BOM = ชีตบันทึกมือ, ไม่มีผู้อนุมัติ/วันมีผล
4. **คงคลังกรอกมือ** ในแต่ละใบ ไม่เชื่อมคลังจริง จึงไม่มียอดจองข้ามใบ (ใบสองใบนับของชิ้นเดียวกัน)
5. **แผนกเห็นเฉพาะกระดาษ**: RB/GR/PT/BG รับงานจากชีต WIP ที่พิมพ์ ความคืบหน้าไม่ไหลกลับเข้าใบสั่งผลิต
6. **สูตรยางกับ BOM ไม่เชื่อมกัน**: BOM รู้แค่รหัสคอมปาวด์ RubberFlow รู้ PHR แต่ไม่รู้ว่าใบไหนต้องการเส้นยางรุ่นไหนเท่าไร

## 2. หลักการออกแบบ

1. **Item master เดียว, BOM หลายชั้นจริง** เก็บความสัมพันธ์พ่อ-ลูกครั้งเดียว (SE → RB ไม่คัดลอกตาม FG) ส่วน "ใบคำนวณแบบแบน" เป็นผลการระเบิดที่สร้างเมื่อต้องการ
2. **แต่ละแผนกเป็นเจ้าของ BOM ของชิ้นที่ตนผลิต** และแก้ได้เฉพาะชั้นของตน (ดูตาราง §3.3) ฝ่ายวางแผนเป็นเจ้าของชั้น FG และหัวใบสั่งผลิต
3. **ทุกการบันทึก BOM เป็น revision ใหม่พร้อมผู้บันทึกและสิ่งที่เปลี่ยน** (ไม่มีขั้นอนุมัติ ดู §3.3) ใบสั่งผลิตล็อก revision ที่ใช้ตอนปล่อยผลิต (แทน `BOMSHEET (S)`)
4. **ใบสั่งผลิตเป็นข้อมูล ไม่ใช่ไฟล์** สถานะอยู่ในตาราง การแตกงานรายแผนกเป็น view/ตารางลูก ไม่ใช่ชีต WIP
5. **ทำตามกติกาโปรเจค**: ตารางใหม่เปิดในโหมดทดสอบก่อน (`is_test` + trigger `private.sandbox_row_scope()` ลงทะเบียน `private.sandbox_unguarded_tables()`) · RLS + deny-all แล้วเปิดผ่าน RPC/`security definer` ที่ตรวจพนักงาน แผนก และสถานะ · `audit_logs` ทุกการอนุมัติ/เปลี่ยนสถานะ · migration ก่อน Pilot Web ตามหัวข้อ "Deployment order" ใน `AGENTS.md`
6. **ไม่ตัดขาด Excel ทันที** ระบบ export `BOMSHEET` / `BOMASKSHEET` / `WIP-*` ในรูปเดิมได้ตลอดช่วงเปลี่ยนผ่าน

RPC (ผู้เรียกต้องเป็น admin ในโหมดทดสอบที่ใช้ persona): `app_bom_master()` คืน snapshot ทั้งชุดรูป state v6 พร้อม `version` (โหลดครั้งแรก) · `app_bom_master_since(version)` คืน delta (ตามทันหลัง `BOM_STALE` และเมื่อหน้ากลับมาโฟกัส) · `app_bom_save_master(changes, base_version, action)` บันทึกชุดการเปลี่ยนแปลงในธุรกรรมเดียว คืน delta ตั้งแต่ `base_version` · อ่านได้ทุก persona · เขียนได้เฉพาะแผนก `PP` และบทบาท department_manager / assistant_factory_manager / factory_manager / general_manager / admin (นอกนั้น `BOM_FORBIDDEN`)

**การชนกันของผู้ใช้หลายคน (รายระเบียน)** ตัวนับ `version` ทั้งชุดคงไว้เรียงลำดับ แต่ `app_bom_save_master` ให้ `BOM_STALE` เฉพาะเมื่อระเบียนที่คำสั่งนี้แตะถูกคนอื่นแก้ (`changed_version > base_version`): เขียนทับแถวที่มีอยู่ · สร้างกุญแจที่มีแล้ว · ลบแถวนั้น · เขียนทับ/ลบชุดสี/แพ็กเกจที่คนอื่นเพิ่งลบ · เพิ่ม revision ใหม่ของชิ้นที่คนอื่นเพิ่ง/แก้ revision ไว้ (สองคนบันทึก revision ใหม่ของชิ้นเดียวกันพร้อมกัน คนที่สองถูกปฏิเสธ) ส่วนระเบียนอื่นที่คนอื่นแก้ระหว่างนั้นไม่ขวาง (ต่างชิ้นกันบันทึกพร้อมกันได้ทั้งคู่) · `base_version` ต้อง 0 ถึง version ปัจจุบัน (นอกช่วง = `BOM_INVALID_PAYLOAD`)

**delta** `{ version, changes: { <ชุด>: { upsert: [เรคอร์ดเต็มรูปเดียวกับ snapshot], delete: [{base, code}] } } }` ครบทุกชุด (แปดชุดข้อมูลหลัก + `customers` `orders` `jobs` ตั้งแต่ PR 2 delete ของ `jobs` เป็น `{id, code}`) มีทุกการเปลี่ยนแปลงตั้งแต่ `base_version` ของทุกคน (รวม BOM ที่เซิร์ฟเวอร์ตั้ง `superseded` และชุดสี/แพ็กเกจที่ลบ) client รวมเข้าชุดข้อมูลตามกุญแจ (`code` / `id` / `base+code`) แล้วตั้ง `version` จึงตามทันได้ในรอบเดียวแม้ snapshot ใหญ่ (BOM ~30,000 บรรทัด ~1.5 MB) · `BOM_STALE` → client เรียก `app_bom_master_since` แล้วย้อน action นั้น

### 3.2 กฎ BOM ที่ฐานข้อมูลบังคับ

- ลูกต้องมีอยู่ ปริมาณ > 0 ขั้นที่ 1–20 ลูกซ้ำในบรรทัดเดียวกันไม่ได้ · ของซื้อ/สูตรยางเป็นพ่อไม่ได้ · เส้นยาง (RB) มีลูกได้เฉพาะสูตรยาง (CP) บรรทัดเดียวและต้องตรงกับ `rubber.compound` · CP อยู่ได้เฉพาะใต้ RB
- ห้ามวงจร (recursive CTE บน BOM ที่ `approved` หลังเขียน เพดาน 30 ชั้น)
- revision แก้ไม่ได้: เรคอร์ดที่มีแล้วเปลี่ยนได้เฉพาะ `approved` → `superseded` (เวลาตั้งโดยเซิร์ฟเวอร์) แผนกเจ้าของ และ changeLog ต่อท้าย · revision ใหม่ต้องเป็นสูงสุดเดิม + 1 และตัวที่ `approved` อยู่ถูกเซิร์ฟเวอร์ตั้ง `superseded` ในคำสั่งเดียวกัน
- เปลี่ยนชนิดของชิ้นที่มี BOM แล้วไม่ได้ · audit 1 แถวต่อการบันทึก (ชื่อ action ของ client + จำนวนต่อส่วน ไม่เก็บ payload)
- `qty_per_parent` ของ RB ใต้ SE (คำนวณจากข้อมูลการตัด) ยังคำนวณที่ client ฐานข้อมูลเก็บค่าที่ส่งมา

### 3.3 ใครสร้าง/แก้ BOM และแผนกเจ้าของชั้นไหน

**ตัดสินแล้ว 29 ต.ค. 2026** (ผู้ใช้): จุดสร้าง BOM ต้องมีจุดเดียวเหมือน MAIN ของ Excel — ฝ่ายวางแผนกับผู้จัดการฝ่ายโรงงาน (และผู้ดูแลระบบ) สร้าง/แก้ item และ BOM **ทุกชั้นจากหน้าเดียว** บันทึกแล้วใช้ได้ทันที **ไม่มีขั้นอนุมัติ** ระบบเก็บทุกการบันทึกเป็น revision พร้อมผู้บันทึกและสิ่งที่เปลี่ยน (แทน "รายการเปลี่ยนแปลง" ในชีต) ตารางข้างล่างจึงเหลือความหมายเดียวคือ "แผนกเจ้าของ" ของชิ้นงาน ใช้แยกงานรายแผนกตอนปล่อยผลิตและใช้แจ้งแผนกเมื่อชั้นของเขาถูกแก้ ไม่ใช่เงื่อนไขสิทธิ์ (ในฐานข้อมูล: `bom_boms.status` เหลือ `approved`/`superseded`; สิทธิ์เขียน = แผนก PP หรือผู้จัดการแผนกขึ้นไป ไม่เทียบ `owner_dept`)

| ชั้น BOM | แผนกเจ้าของ (ใช้แยกงาน/แจ้งเตือน) | ข้อมูลที่ดูแล |

ยังอยู่ที่ client: การคำนวณระเบิด BOM และปริมาณงานสุทธิ (`rules.explode` / `netRequirements`) ตัวเลขที่ผู้วางแผนส่งมาถูกเก็บตามที่ส่ง (ตรวจรูปและขนาดเท่านั้น) ถ้าจะให้ฐานข้อมูลคำนวณเองต้องพอร์ตเพิ่มและมี unit test เทียบกับตัวอย่างจริงจากไฟล์ `Material_Megaform 26017.xlsm` (เช่น `MEGA-ST-01(P)-Y` × 80 → `RB-B0006-02-202-18-70` ต้องเบิก 7.74 ชิ้น)

## 4. เชื่อมกับใบสั่งผลิตของ RubberFlow

### 4.1 สิ่งที่มีตอนนี้

RubberFlow (`#/rubberflow` โหมดทดสอบ ข้อมูลใน `localStorage`) มีใบสั่งผลิต `WO` = สูตร (`recipeId` คอมปาวด์ PHR ที่อนุมัติแล้ว) + `targetQty` ในหน่วยของสูตร + ลูกค้า/PO/สี/วันเริ่ม-ส่ง · `createRequisition` ระเบิดสูตรเป็นกิโลกรัมต่อ batch และจอง FEFO · สถานี ผสม → รีด → อบ → ตกแต่ง นับผลผลิตเข้า `producedQty` และปิดใบเมื่อครบ

สิ่งที่ขาด: WO ไม่รู้ว่าทำ "เส้นยางรุ่นไหน" (รหัส RB) ให้ "ใบ PI ไหน" และ GR ไม่รู้ว่าเส้นยางออกมาแล้วกี่เส้น

### 4.2 จุดเชื่อม

```text
PI (bom_production_orders) ── ปล่อยผลิต ──> bom_department_jobs (department = RB)
        │                                            │ หนึ่งแถวต่อรหัส RB: qty_planned (เส้น/kg/ม้วน), due_rb
        │                                            ▼
        │                              RubberFlow: "รับงานจาก BOM" → WO
        │                                recipe  = bom_compounds(compound_code).rubberflow_recipe_id
        │                                target  = qty_planned ในหน่วย RB
        │                                kg คอมปาวด์ ≈ qty × kg_per_roll (หรือ weight_g/1000) × (1 + scrap)
        │                                sourceRef = { pi_number, job_id, rb_item_code }
        │                                            │
        │                      ผสม → รีด → อบ → ตกแต่ง (producedQty ในหน่วย RB)
        │                                            │
        ▼                                            ▼
bom_department_jobs.qty_done ◀── รายงานผลผลิต ─── WO completed / partial
        │
        └─> งาน GR (SE จาก RB) เริ่มได้เมื่อรับมอบจาก RB (Gatekeeper เดิมของ RubberFlow)
```

กติกา:
- WO หนึ่งใบรับได้หลาย job ที่ใช้คอมปาวด์และขนาดเดียวกัน (รวม PI หลายใบในรอบรีดเดียว) จึงเป็นตาราง `rubberflow_wo_sources` (WO ↔ job, qty จัดสรร) ไม่ใช่ FK เดี่ยว
- `targetQty` ใน RubberFlow ต้องเป็นหน่วยของชิ้น RB (เส้น/ชิ้น/ม้วน/kg) ไม่ใช่ `yieldPerKg` ของสูตร; เพิ่ม `kgPerUnit` ต่อชิ้น RB จาก `bom_item_rubber` แทน
- ผลผลิตที่ GR รับมอบ (`receiveTransfer`) คือตัวนับ `qty_done` ของงาน RB ไม่ใช่ตัวเลขที่ RB พิมพ์เอง (ตรงกับหลัก Gatekeeper)
- ของเสีย/NCR ของ RubberFlow อ้าง `job_id` เพื่อสืบย้อนถึง PI และ FG

### 4.3 ลำดับการเชื่อม (เพราะ RubberFlow ยังไม่อยู่บนฐานข้อมูล)

| ขั้น | RubberFlow | ฐานข้อมูล |
|---|---|---|
| A. อ่านอย่างเดียว | หน้า "ใบสั่งผลิต" เพิ่มปุ่ม **รับงานจาก BOM**: เรียก RPC `bom_rb_jobs_open()` (โหมดทดสอบ) แสดงงาน RB ที่ปล่อยแล้ว เลือกแล้วสร้าง WO ใน `localStorage` พร้อม `sourceRef`; ปุ่ม **รายงานผลผลิตกลับ** เรียก RPC `bom_job_report(job_id, qty)` | เพิ่มเฉพาะ RPC อ่านงาน + บันทึก `qty_done` (ตรวจบทบาท RB/ผู้จัดการ) |
| B. ย้าย WO ขึ้นฐานข้อมูล | `orders`/`requisitions`/`lots`/`transfers` ของ RubberFlow เป็นตารางจริง (ตาม README: ต้องมี migration/RPC/เทสต์ของตัวเอง) | `rubberflow_orders.source_job_id`, trigger อัปเดต `bom_department_jobs.qty_done` จากการรับมอบ |
| C. สูตรยาง | ย้าย `recipes` ขึ้นฐานข้อมูลเป็น `bom_compounds` + `bom_compound_revisions(items PHR, batchKg, dumpTemp …)` ให้ BOM และ RubberFlow ใช้ตารางเดียว | สถานะอนุมัติสูตรของ RubberFlow เป็นของตาราง ไม่ใช่ `localStorage` |

**สถานะ (7 พ.ย. 2026, โหมดทดสอบ)**: ขั้น B/C ส่วนแรกทำแล้ว — migration `20261107010000_rubberflow_core.sql` ย้าย `materials`, `recipes` (PHR ทุก revision อนุมัติโดยหัว RB) และ `orders` (WO) ของ RubberFlow ขึ้นฐานข้อมูลเป็นตาราง `rf_*` (ชื่อจริงต่างจากร่างในตารางข้างบน) ใช้กลไกเดียวกับ BOM · WO ผูกงาน RB ด้วย `sourceJobId`: เซิร์ฟเวอร์ตรวจงาน เขียน `bom_jobs.external_ref` และเดินตัวนับ BOM ในธุรกรรมเดียวกัน (ลำดับล็อก rf ก่อน bom) · ขั้น A "รายงานผลผลิตกลับ" ทำเป็นการป้อนกลับตอน WO ปิด (ยอดผลิตของ WO ใบนั้นถูกบวกเข้า `qty_done` พร้อมรายงานในงาน + สถานะงาน + ใบ PI released → in_progress ป้อนครั้งเดียวต่อ WO) · ยกเลิก WO ที่ผูกงานล้างการผูกของงานเอง (ยอดเดิมคงอยู่) แล้วผูก WO ใหม่ได้ เพราะใบส่งมอบ (`transfers`) ยังอยู่ใน localStorage · คอมปาวด์ของ BOM ผูกกับรหัสสูตรใน `rf_recipes` ได้เฉพาะรหัสที่มีอยู่

**ปล่อยผลิตแล้วเปิด WO ให้เอง (8 พ.ย. 2026, โหมดทดสอบ, migration `20261108020000_bom_release_opens_rubberflow_orders.sql`)**: ตอน `releaseOrder` ในธุรกรรมเดียวกับที่สร้างงาน เซิร์ฟเวอร์เปิด WO (`planned`, `source_job_no` = งาน, `external_ref.auto = true`) ให้ทุกงาน RB ที่เส้นยางมีรหัสสูตรยาง → คอมปาวด์ผูกสูตร (`bom_compounds.recipe_id`) → สูตร approved ใน `rf_recipes` และยังมียอดให้ผลิตกับคำนวณกก. ได้ (สูตรกก.เดียวกับ `rbJobKg` เผื่อ 5%) · งานที่เปิดไม่ได้ถูกข้ามพร้อมเหตุผลในคำตอบ (`rubberflow.skipped`) การปล่อยผลิตไม่ล้ม และยังสร้าง WO ด้วยมือจากหน้างานต่อได้ · งานยังเป็น `queued` ใบยังเป็น `released` จนกว่า SR จะรับมอบใบส่งมอบใบแรก · ยกเลิกใบ/เปิดใบกลับเป็นร่าง: WO `planned`/`released` ถูกยกเลิกให้ (ทั้งที่เปิดเองและด้วยมือ) WO ที่เริ่มผลิตแล้ว = `BOM_RF_ORDER_STARTED` (ปิดหรือยกเลิก WO ใน RubberFlow ก่อน) · ทั้งสองฝั่งเดินตัวนับ RF และเขียน audit `bom:<action>` ให้หน้า RubberFlow เห็น · `app_bom_save_master` กับ `app_rf_save` ล็อก advisory เดียวกันก่อน กัน deadlock จากลำดับล็อก bom/rf ที่สลับกัน · โหมดในเครื่อง (ไม่มี Supabase) ไม่เปิด WO อัตโนมัติ

**รอบที่ 2 (8 พ.ย. 2026, โหมดทดสอบ)**: ที่เหลือทั้งหมดขึ้นฐานข้อมูลแล้ว (migration `20261108010000_rubberflow_shopfloor.sql`: `materialLots`, `requisitions`, `lots`, `transfers`, `fgBoxes`, `qcRecords`, `ncrs`, `molds` เป็นตาราง `rf_*`) และ **การป้อนกลับย้ายมาเป็นตอน SR รับมอบใบส่งมอบ** (`receiveTransfer`) ตามที่ผู้ใช้เลือก: ทุกใบส่งมอบที่รับมอบและล็อตเป็นของ WO ที่ผูกงาน BOM ต่อรายงาน `good` = `qtyReceived` (ล็อตหน่วย kg แปลงเป็นหน่วยของ WO ด้วย `kgPerUnit`) บวก `qty_done` ในธุรกรรมเดียวกับการรับมอบ (ข้ามเมื่องาน done / ใบ PI ปิดแล้ว / ไม่มี `kgPerUnit` สำหรับล็อต kg) การป้อนกลับตอนปิด WO (รอบที่ 1) เลิกใช้ และปิด WO ไม่ต้องมียอดผลิต · ข้อสังเกต: ใบส่งมอบทุกสถานีรวมสถานีผสม (kg) ป้อนกลับ จึงรับยอดซ้ำเมื่อชิ้นงานเดียวกันถูกรับมอบหลายสถานี (ตามที่ผู้ใช้กำหนด) · ตาราง `rubberflow_wo_sources` (หลายงานต่อ WO) ยังไม่ทำ รอบนี้ WO หนึ่งใบผูกงาน BOM ได้หนึ่งงาน (ดัชนี unique บางส่วนบน `rf_orders.source_job_no`)

**จัดซื้อเคมีของ RubberFlow (10 พ.ย. 2026, โหมดทดสอบ, migration `20261110010000_rf_purchase_orders.sql`, PR 1 จาก 2)**: ตาราง `rf_purchase_orders` (ใบสั่งซื้อ `ordered` → `received` / `cancelled` บรรทัดเป็น jsonb) และช่อง `safetyKg` / `shelfLifeDays` ของวัตถุดิบ — ปล่อยผลิตใบ PI แล้ว Pilot Web คำนวณเคมีที่ WO ที่เปิดต้องใช้เทียบสต็อก (ตัวคำนวณฝั่ง client) และเปิดหน้าต่างสั่งซื้อเมื่อขาด · ST รับเข้าทีละบรรทัดและเซิร์ฟเวอร์สร้างล็อตวัตถุดิบในคำสั่งเดียวกัน · ชื่อ `purchaseOrders` / บรรทัดเป็นชื่อกลาง ๆ เพื่อให้ PR 2 (สต็อกและการเบิกชิ้นส่วนจัดซื้อของ BOM ในหน้าต่างเดียวกัน) ต่อรูปเดิมได้ · กติกาและสิทธิ์ดูหัวไฟล์ migration และหัวข้อ "ฐานข้อมูลรอบที่ 3" ใน `README.md`

**จัดซื้อ PR 2: คลังของซื้อและเบิกจ่ายรายใบ PI (11 พ.ย. 2026, โหมดทดสอบ, migration `20261111010000_bom_part_stock.sql`)**: ตาราง `bom_stock` (ยอดคงเหลือ + สต็อกขั้นต่ำต่อรหัสของซื้อ) และ `bom_stock_moves` (ประวัติ count / receive / issue เซิร์ฟเวอร์เขียนเอง) — ยอดตั้งต้นมาจาก ST นับที่หน้า **คลังของซื้อ** · ปล่อยผลิตสร้างงาน ST (PURCHASED) ต่อรายการของซื้อ ยอดเต็มไม่หักยอดนับตามใบ · ST กดเบิกจ่ายครั้งเดียวต่อใบ (all-or-none, ขาด = ไม่จ่ายเลยและเปิดหน้าต่างสั่งซื้อ) · ใบสั่งซื้อใบเดียวกับเคมีมีบรรทัดของซื้อ รับเข้าเพิ่มยอดคงเหลือ ไม่มีล็อต/วันหมดอายุ · `partNeeds` ใน `modules/bom-rules.js` คิด ต้องใช้ − (คงเหลือ − จองแล้ว + สั่งค้างรับ) แบบเดียวกับ `chemicalNeeds` · รายละเอียดกติกาและสิทธิ์อยู่ที่หัวไฟล์ migration

**คืนของซื้อเข้าสต็อก (12 พ.ย. 2026, โหมดทดสอบ, migration `20261112010000_bom_part_returns.sql`)** — ST หรือฝ่ายวางแผนคืนของซื้อที่เบิกจ่ายแล้วได้สองทางที่หน้าใบ PI โดยต้องระบุเหตุผล 1-200 ตัวอักษร (เก็บในประวัติสต็อก `bom_stock_moves.note`): **ยกเลิกการเบิกจ่าย** (action `undoOrderParts`) คืนของที่เบิกจ่ายทั้งใบเข้าสต็อกและงาน ST กลับไปรอเบิกจ่าย (สถานะใบไม่เปลี่ยน เบิกจ่ายใหม่ ยกเลิกใบ หรือเปิดใบกลับมาแก้ได้เมื่อไม่มีงานแผนกอื่นเริ่มแล้ว; ใบที่ปล่อยผลิตแล้วและยังไม่ปิด) และ **คืนของเหลือ** (action `returnOrderParts`) คืนบางรายการตามจำนวนที่พิมพ์ งานยังเป็นเบิกจ่ายแล้ว (ใบที่ปล่อยผลิตแล้วรวมใบที่ปิดแล้ว ใบที่ยกเลิกคืนไม่ได้) · ยอดที่คืนได้ต่อรายการ = ยอดเบิกจ่าย - ยอดที่คืนไปแล้ว นับตั้งแต่การเบิกจ่ายล่าสุดของรายการนั้นในใบ (หลังยกเลิกการเบิกจ่ายแล้วเบิกจ่ายใหม่ ของเหลือรอบก่อนไม่นับ) · ผลคำนวณที่เซิร์ฟเวอร์ทั้งหมด หน้าส่งเฉพาะแถวคำขอ `{ orderId, mode, reason, lines? }` ในส่วน `partReturns` · ประวัติสต็อกมีชนิด **คืน** และช่อง `note`.

## 9. เรื่องที่ต้องตัดสินใจก่อนเริ่มเฟส 1

1. **SE คือผลงานของแผนกไหน** — ข้อมูลระบุ `แผนกผู้ผลิต = SE` แต่ `MAIN` มีกำหนดเสร็จ GR ไม่มี SE; เอกสารนี้สมมติว่า GR ตัด RB เป็น SE (เจาะ/คัดแยก) ถ้าจริงเป็นแผนก SE แยก ให้เพิ่มแถวในตาราง §3.3 เท่านั้น
2. ~~การอนุมัติ BOM~~ — **ตัดสินแล้ว**: ไม่มีขั้นอนุมัติ บันทึกแล้วใช้ได้ทันที เก็บ revision (ดู §3.3)
3. ~~ขอบเขตการแก้ของ RB กับ QC~~ — **ตัดสินแล้ว**: ฝ่ายวางแผน/ผู้จัดการแก้ทุกชั้นรวมคอมปาวด์ของ RB ได้ QC ไม่ต้องอนุมัติ (สูตร PHR ยังอนุมัติใน RubberFlow ตามเดิม)
4. **หน่วยของ RB ใน WO**: นับเป็นเส้น ม้วน หรือ kg เป็นหลัก (วันนี้ปนกัน 3 แบบ) — เสนอ: เก็บทั้ง `kg_per_roll` และ `pcs_per_roll` แล้ว WO ใช้ kg เป็นหน่วยผลิต แสดงเส้น/ม้วนเทียบเท่า
5. **PI revision** (`แก้ไขฉบับที่`): แก้จำนวนหลังปล่อยผลิต = revision ใหม่และระเบิดใหม่เฉพาะส่วนต่าง หรือยกเลิกแล้วเปิดใบใหม่ — เสนอ revision ใหม่ โดยงานที่ `done` แล้วไม่ถูกแตะ
