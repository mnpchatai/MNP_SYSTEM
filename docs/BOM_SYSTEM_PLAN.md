### 1.2 โครงสร้างข้อมูล BOM ที่ซ่อนอยู่ในชีต

- **สินค้าสำเร็จรูป (FG)** รหัส = `<ฐาน>(<แพ็กเกจ>)-<ชุดสี>` เช่น `MEGA-ST-01(P)-Y` ฐาน `MEGA-ST-01`
- **บรรทัดส่วนประกอบ** มี `รหัสแผนกที่ผลิต` 5 ค่า: `ST` (ซื้อ/คลัง 15,422 บรรทัด) · `SE` (ชิ้นยางย่อย 6,514) · `RB` (เส้นยาง 6,927) · `PK` (ตัวสินค้า 1,384) · `BG` (3)
  และ `แผนกผู้ผลิต` เป็น **คู่ ผู้ใช้-ผู้ผลิต** เช่น `PK-ST` (PK ใช้ของจากคลัง) `PT-ST` (PT ใช้เม็ดพลาสติก) `BG-ST` (BG ใช้ผ้า/ซิป) `PK-PT` `PK-BG` `BG-PT` `GR-ST` `PK-PK`
- **BOM เป็นหลายชั้นแต่ถูกเก็บแบบแบน**: FG → SE → RB (บรรทัด RB ตามหลัง SE และคอลัมน์ `ชิ้นงานถัดไปของ RB นี้` ชี้กลับไปที่ SE) · FG → PT → เม็ดพลาสติก (ST) · FG → BG → ผ้า/ซิป (ST) · FG → บรรจุภัณฑ์ (ST) ต้นไม้เดียวกันจึงถูกคัดลอกซ้ำในทุก FG ที่ใช้
- **รหัสชิ้นงานยางเข้ารหัสคุณสมบัติในตัว**
  `RB-<สูตรยาง>-<ประเภท 01 ตัน/02 มีรู/03 แผ่น>-<สี RB>-<ความยาว>-<รู/ความหนา>-<วงนอก>` เช่น `RB-B0006-02- -202-18-70`
  `SE-<สินค้า>-<สี>-<ความยาว>-<รู/หนา>-<วงนอก>` เช่น `SE-ST01--100-18-65`
  สี = แม่สี + เฉด สูงสุด 3 สี (`OR`+`01` → `OR01`) · `สูตรยาง` คือรหัสคอมปาวด์ (พบ 40 รหัส: `A1802 A2003 … B0006 … C1302`) ซึ่งตรงกับ "สูตรยาง (PHR)" ของ RubberFlow
- **สูตรปริมาณ** (จาก BOMSHEET): RB ต่อ SE = `1 / (จำนวน GR ตัดได้ต่อเส้น × จำนวน SE ต่อ 1 GR)` (ถ้าหน่วย RB เป็นกิโลกรัมใช้ `น้ำหนัก/1000`) · ต้องเบิก = จำนวน FG × จำนวนใช้ต่อ FG · ต้องผลิต/สั่งซื้อ = ต้องเบิก − คงคลัง (RB หักเศษตัดด้วย) · น้ำหนักต่อชิ้น/ต่อเส้น และตัวอย่างชั่ง 10 ครั้ง อยู่ใน master (6,342 บรรทัดมีค่าชั่ง)
- **ธงกระบวนการ** ใน master มี 9 คอลัมน์ แต่ใช้จริง 2: `เจาะ` (6,746) และ `คัดแยก` (7,151)

### 1.3 ข้อจำกัดที่ระบบใหม่ต้องแก้

1. **ไม่มี master เดียว**: `DATA` ถูกคัดลอกไปอยู่ในทุกไฟล์ PI (20 MB ต่อไฟล์) แก้ master แล้วใบเก่าไม่รู้ และสองชุด (ของเล่น/อุตสาหกรรม) แยกกัน
2. **คุณภาพรหัส**: 1,046 บรรทัดไม่มีรหัส (`-`/`0`) เป็นชิ้นที่ PK ทำเองหรือของ "ตามความเหมาะสม" · รหัส RB/SE 151 ตัวสะกดต่างกัน (ช่องว่าง/ขีดซ้ำ เช่น `RB-B0005-02--132-9-25` กับ `RB-B0005-02- -132-9-25`) · หน่วยนับ 356 แบบสะกด (`ชิ้น/pcs` `ชิ้น/pcs.` `กก.` `กิโลกรัม` `ม้วน(50M)` `ม้วน (50M)`) · หน่วยปนน้ำหนัก/จำนวนต่อแพ็ก (`กก.(112pcs)` `ชิ้น(20g)`)
3. **สถานะและการอนุมัติไม่มีในข้อมูล**: สถานะใบ = โฟลเดอร์, การแก้ BOM = ชีตบันทึกมือ, ไม่มีผู้อนุมัติ/วันมีผล
4. **คงคลังกรอกมือ** ในแต่ละใบ ไม่เชื่อมคลังจริง จึงไม่มียอดจองข้ามใบ (ใบสองใบนับของชิ้นเดียวกัน)
5. **แผนกเห็นเฉพาะกระดาษ**: RB/GR/PT/BG รับงานจากชีต WIP ที่พิมพ์ ความคืบหน้าไม่ไหลกลับเข้าใบสั่งผลิต
6. **สูตรยางกับ BOM ไม่เชื่อมกัน**: BOM รู้แค่รหัสคอมปาวด์ RubberFlow รู้ PHR แต่ไม่รู้ว่าใบไหนต้องการเส้นยางรุ่นไหนเท่าไร

## 2. หลักการออกแบบ

1. **Item master เดียว, BOM หลายชั้นจริง** เก็บความสัมพันธ์พ่อ-ลูกครั้งเดียว (SE → RB ไม่คัดลอกตาม FG) ส่วน "ใบคำนวณแบบแบน" เป็นผลการระเบิดที่สร้างเมื่อต้องการ
2. **แต่ละแผนกเป็นเจ้าของ BOM ของชิ้นที่ตนผลิต** และแก้ได้เฉพาะชั้นของตน (ดูตาราง §3.3) ฝ่ายวางแผนเป็นเจ้าของชั้น FG และหัวใบสั่งผลิต
3. **ทุก BOM มี revision + สถานะ + ผู้อนุมัติ** ใบสั่งผลิตล็อก revision ที่ใช้ตอนปล่อยผลิต (แทน `BOMSHEET (S)`)
4. **ใบสั่งผลิตเป็นข้อมูล ไม่ใช่ไฟล์** สถานะอยู่ในตาราง การแตกงานรายแผนกเป็น view/ตารางลูก ไม่ใช่ชีต WIP
5. **ทำตามกติกาโปรเจค**: ตารางใหม่เปิดในโหมดทดสอบก่อน (`is_test` + trigger `private.sandbox_row_scope()` ลงทะเบียน `private.sandbox_unguarded_tables()`) · RLS + deny-all แล้วเปิดผ่าน RPC/`security definer` ที่ตรวจพนักงาน แผนก และสถานะ · `audit_logs` ทุกการอนุมัติ/เปลี่ยนสถานะ · migration ก่อน Pilot Web ตามหัวข้อ "Deployment order" ใน `AGENTS.md`
6. **ไม่ตัดขาด Excel ทันที** ระบบ export `BOMSHEET` / `BOMASKSHEET` / `WIP-*` ในรูปเดิมได้ตลอดช่วงเปลี่ยนผ่าน

กฎ:
- พ่อหนึ่งตัวมี `approved` ได้ revision เดียวต่อช่วงเวลา (unique partial index) อนุมัติ revision ใหม่ = ตัวเก่า `superseded` อัตโนมัติในทรานแซกชันเดียว

- `qty_per_parent` ของ RB ใต้ SE คำนวณจาก `cut_length_cm` `pcs_per_roll` `se_per_gr` ของ `bom_item_rubber` ให้อัตโนมัติ (ผู้ใช้กรอกข้อมูลการตัด ไม่ต้องกรอกอัตราส่วน) และยังแก้ทับได้พร้อมเหตุผล

### 3.3 ใครสร้าง/แก้ BOM และแผนกเจ้าของชั้นไหน

**ตัดสินแล้ว 29 ต.ค. 2026** (ผู้ใช้): จุดสร้าง BOM ต้องมีจุดเดียวเหมือน MAIN ของ Excel — ฝ่ายวางแผนกับผู้จัดการฝ่ายโรงงาน (และผู้ดูแลระบบ) สร้าง/แก้ item และ BOM **ทุกชั้นจากหน้าเดียว** บันทึกแล้วใช้ได้ทันที **ไม่มีขั้นอนุมัติ** ระบบเก็บทุกการบันทึกเป็น revision พร้อมผู้บันทึกและสิ่งที่เปลี่ยน (แทน "รายการเปลี่ยนแปลง" ในชีต) ตารางข้างล่างจึงเหลือความหมายเดียวคือ "แผนกเจ้าของ" ของชิ้นงาน ใช้แยกงานรายแผนกตอนปล่อยผลิตและใช้แจ้งแผนกเมื่อชั้นของเขาถูกแก้ ไม่ใช่เงื่อนไขสิทธิ์ (ในฐานข้อมูล: `bom_headers.status` เหลือ `approved`/`superseded`, ตัด `pending_approval`; สิทธิ์เขียน = บทบาทวางแผน/ผู้จัดการ ไม่เทียบ `owner_department_id`)

| ชั้น BOM | แผนกเจ้าของ (ใช้แยกงาน/แจ้งเตือน) | ข้อมูลที่ดูแล |
|---|---|---|
| FG → ส่วนประกอบชั้นแรก (SE, PT, BG, บรรจุภัณฑ์) | PK | จำนวนต่อชุด แพ็กเกจ ชุดสี |

| RB (เส้นยาง) | RB | คอมปาวด์ ขนาด สี น้ำหนักต่อเส้น/ต่อชิ้น (สูตร PHR อยู่ที่ RubberFlow) |
| PT → เม็ดพลาสติก | PT | กรัมต่อชิ้น เม็ดสี |
| BG → ผ้า ซิป เทป | BG | หลา/เมตรต่อชิ้น |
| ชิ้นซื้อ (`PURCHASED`) item master | ST | รหัส หน่วย ขนาดแพ็ก |
| สูตรยาง (PHR) | RubberFlow (QC/ผู้จัดการ อนุมัติ) ตามที่มีอยู่ | เชื่อมผ่าน `bom_compounds` |

สิทธิ์อ่าน: ทุกคนที่ล็อกอินอ่าน BOM ปัจจุบันและประวัติ revision ได้ สิทธิ์เขียน: บทบาทวางแผน/ผู้จัดการ/ผู้ดูแลเท่านั้น

## 4. เชื่อมกับใบสั่งผลิตของ RubberFlow

### 4.1 สิ่งที่มีตอนนี้

RubberFlow (`#/rubberflow` โหมดทดสอบ ข้อมูลใน `localStorage`) มีใบสั่งผลิต `WO` = สูตร (`recipeId` คอมปาวด์ PHR ที่อนุมัติแล้ว) + `targetQty` ในหน่วยของสูตร + ลูกค้า/PO/สี/วันเริ่ม-ส่ง · `createRequisition` ระเบิดสูตรเป็นกิโลกรัมต่อ batch และจอง FEFO · สถานี ผสม → รีด → อบ → ตกแต่ง นับผลผลิตเข้า `producedQty` และปิดใบเมื่อครบ

สิ่งที่ขาด: WO ไม่รู้ว่าทำ "เส้นยางรุ่นไหน" (รหัส RB) ให้ "ใบ PI ไหน" และ GR ไม่รู้ว่าเส้นยางออกมาแล้วกี่เส้น

### 4.2 จุดเชื่อม

```text
PI (bom_production_orders) ── ปล่อยผลิต ──> bom_department_jobs (department = RB)
        │                                            │ หนึ่งแถวต่อรหัส RB: qty_planned (เส้น/kg/ม้วน), due_rb
        │                                            ▼
        │                              RubberFlow: "รับงานจาก BOM" → WO
        │                                recipe  = bom_compounds(compound_code).rubberflow_recipe_id
        │                                target  = qty_planned ในหน่วย RB
        │                                kg คอมปาวด์ ≈ qty × kg_per_roll (หรือ weight_g/1000) × (1 + scrap)
        │                                sourceRef = { pi_number, job_id, rb_item_code }
        │                                            │
        │                      ผสม → รีด → อบ → ตกแต่ง (producedQty ในหน่วย RB)
        │                                            │
        ▼                                            ▼
bom_department_jobs.qty_done ◀── รายงานผลผลิต ─── WO completed / partial
        │
        └─> งาน GR (SE จาก RB) เริ่มได้เมื่อรับมอบจาก RB (Gatekeeper เดิมของ RubberFlow)
```

กติกา:
- WO หนึ่งใบรับได้หลาย job ที่ใช้คอมปาวด์และขนาดเดียวกัน (รวม PI หลายใบในรอบรีดเดียว) จึงเป็นตาราง `rubberflow_wo_sources` (WO ↔ job, qty จัดสรร) ไม่ใช่ FK เดี่ยว
- `targetQty` ใน RubberFlow ต้องเป็นหน่วยของชิ้น RB (เส้น/ชิ้น/ม้วน/kg) ไม่ใช่ `yieldPerKg` ของสูตร; เพิ่ม `kgPerUnit` ต่อชิ้น RB จาก `bom_item_rubber` แทน
- ผลผลิตที่ GR รับมอบ (`receiveTransfer`) คือตัวนับ `qty_done` ของงาน RB ไม่ใช่ตัวเลขที่ RB พิมพ์เอง (ตรงกับหลัก Gatekeeper)
- ของเสีย/NCR ของ RubberFlow อ้าง `job_id` เพื่อสืบย้อนถึง PI และ FG

### 4.3 ลำดับการเชื่อม (เพราะ RubberFlow ยังไม่อยู่บนฐานข้อมูล)

| ขั้น | RubberFlow | ฐานข้อมูล |
|---|---|---|
| A. อ่านอย่างเดียว | หน้า "ใบสั่งผลิต" เพิ่มปุ่ม **รับงานจาก BOM**: เรียก RPC `bom_rb_jobs_open()` (โหมดทดสอบ) แสดงงาน RB ที่ปล่อยแล้ว เลือกแล้วสร้าง WO ใน `localStorage` พร้อม `sourceRef`; ปุ่ม **รายงานผลผลิตกลับ** เรียก RPC `bom_job_report(job_id, qty)` | เพิ่มเฉพาะ RPC อ่านงาน + บันทึก `qty_done` (ตรวจบทบาท RB/ผู้จัดการ) |
| B. ย้าย WO ขึ้นฐานข้อมูล | `orders`/`requisitions`/`lots`/`transfers` ของ RubberFlow เป็นตารางจริง (ตาม README: ต้องมี migration/RPC/เทสต์ของตัวเอง) | `rubberflow_orders.source_job_id`, trigger อัปเดต `bom_department_jobs.qty_done` จากการรับมอบ |
| C. สูตรยาง | ย้าย `recipes` ขึ้นฐานข้อมูลเป็น `bom_compounds` + `bom_compound_revisions(items PHR, batchKg, dumpTemp …)` ให้ BOM และ RubberFlow ใช้ตารางเดียว | สถานะอนุมัติสูตรของ RubberFlow เป็นของตาราง ไม่ใช่ `localStorage` |

## 9. เรื่องที่ต้องตัดสินใจก่อนเริ่มเฟส 1

1. **SE คือผลงานของแผนกไหน** — ข้อมูลระบุ `แผนกผู้ผลิต = SE` แต่ `MAIN` มีกำหนดเสร็จ GR ไม่มี SE; เอกสารนี้สมมติว่า GR ตัด RB เป็น SE (เจาะ/คัดแยก) ถ้าจริงเป็นแผนก SE แยก ให้เพิ่มแถวในตาราง §3.3 เท่านั้น
2. ~~การอนุมัติ BOM~~ — **ตัดสินแล้ว**: ไม่มีขั้นอนุมัติ บันทึกแล้วใช้ได้ทันที เก็บ revision (ดู §3.3)
3. ~~ขอบเขตการแก้ของ RB กับ QC~~ — **ตัดสินแล้ว**: ฝ่ายวางแผน/ผู้จัดการแก้ทุกชั้นรวมคอมปาวด์ของ RB ได้ QC ไม่ต้องอนุมัติ (สูตร PHR ยังอนุมัติใน RubberFlow ตามเดิม)
4. **หน่วยของ RB ใน WO**: นับเป็นเส้น ม้วน หรือ kg เป็นหลัก (วันนี้ปนกัน 3 แบบ) — เสนอ: เก็บทั้ง `kg_per_roll` และ `pcs_per_roll` แล้ว WO ใช้ kg เป็นหน่วยผลิต แสดงเส้น/ม้วนเทียบเท่า
5. **PI revision** (`แก้ไขฉบับที่`): แก้จำนวนหลังปล่อยผลิต = revision ใหม่และระเบิดใหม่เฉพาะส่วนต่าง หรือยกเลิกแล้วเปิดใบใหม่ — เสนอ revision ใหม่ โดยงานที่ `done` แล้วไม่ถูกแตะ
